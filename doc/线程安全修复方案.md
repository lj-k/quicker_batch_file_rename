# 线程安全与内存安全修复方案

> 版本：0.01
> 日期：2026-11-18
> 依据：《线程安全与内存安全评审报告》0.01、《线程安全与内存安全分析》0.01
> 目标代码：0.06.21
> 状态：方案稿，未修改代码
> 参与团队：架构组、前端（WPF/UI）组、后端（核心/文件引擎）组、性能组、并发组、开发组、测试组

## 0. 结论摘要

1. 本轮不新增业务功能，只修复生命周期、并发数据契约、资源所有权和失败路径。三套交付方案继续共享同一份源码，输出契约、模板语义、预设结构和执行动作不变。
2. 修复按“先隔离会话，再冻结数据，再明确资源所有权，最后做性能与体验优化”的顺序推进，避免在旧结构上继续叠加补丁。
3. P0共5项，必须在下一稳定版前完成：统一窗口会话与执行会话、布局不可变快照与数据版本、`_layoutWorkerCount`生命周期、Explorer COM所有权释放、哈希缓存代际与失效。
4. P1共8项，与P0同版或紧随版本完成：线程启动失败处理、`RunIndexedParallel`超时与异常上报、幂等`ShutdownSession()`、UI线程禁止同步布局/哈希、全局并发预算、哈希读取共享模式与一致性校验、Process/Dialog/Popup释放、选择读取STA线程消息泵与停止Join。
5. P2共7项，排期完成：跨线程标志volatile化、哈希缓存容量与LRU、单实例保护、BLAKE3缓冲调优、Shell缓存与选择快速判定、`ApplyLayouts`分批刷新、网络路径按主机限流。
6. 发布门禁：P0未完成，不发布长期驻留Quicker进程的稳定版；P1未完成，不宣称“资源长期稳定”；所有批次必须通过核心测试、三方案构建、交付校验和Windows实机压力场景。

## 1. 修复目标、边界与不变量

### 1.1 修复目标

| 目标 | 判定 |
|---|---|
| 消除跨会话写入 | 旧窗口/旧会话的后台线程不能读写新窗口的队列、集合、配置和UI |
| 消除可触发的越界崩溃 | 布局中反复替换输入列表，不出现`IndexOutOfRangeException`或错行 |
| 消除长期资源累积 | 实时获取、关闭/重开、执行/校验不造成COM、句柄、线程、私有内存单调增长 |
| 消除永久卡死 | 线程启动失败、队列失败、回调丢失、网络挂起时，界面可恢复或可关闭 |
| 保证校验码正确 | 文件外部变化后重新获取，不使用旧哈希；旧代际不能覆盖新结果 |
| 保持性能 | 扫描、布局、哈希、执行不明显回退；UI线程不执行长IO/哈希 |

### 1.2 非目标

- 不引入原生BLAKE3 DLL，不改变AVX/AVX2/AVX512F“只用于调度、不执行AVX512指令”的现状。
- 不重做界面布局、筛选、预设、模板编辑器。
- 不改变复制/移动/重命名的文件语义、冲突策略、输出列表契约。
- 不追求“强制终止网络IO”；.NET Framework阻塞式文件IO无法可靠取消，本方案采用会话隔离、超时提示和资源上限降低影响。

### 1.3 必须保持的不变量

| 编号 | 不变量 |
|---|---|
| I-01 | 同一时刻只有一个活动`WindowSession`；所有异步回调先校验会话，再校验数据版本 |
| I-02 | 后台布局只读不可变快照，不直接读`_files`、`_rows`、`_config`、`_hashCache` |
| I-03 | 执行工作线程只读自己的`ExecutionSession`，不读全局`_execQueue`/`_execStop` |
| I-04 | COM、Process、Dialog、Popup、文件流的获取与释放成对，且有明确所有者 |
| I-05 | 任何线程启动、排队、计算、IO失败都必须复位计数并给出可见状态 |
| I-06 | UI线程不执行文件哈希、内容比较、长文件IO；必要等待通过异步状态机完成 |
| I-07 | 三套交付方案的XAML、Aux、输出行为保持同步 |

### 1.4 平台约束

- Quicker自定义窗口辅助代码按C# 5.0编译，方案中的示例不使用字符串插值、`?.`、`nameof`、表达式体成员、`using static`。
- 目标运行时为.NET Framework 4.8；可使用`SemaphoreSlim`、`ConcurrentQueue`、`CountdownEvent`、`Volatile`、`Interlocked`、`Dispatcher`。
- 不使用`Thread.Abort`、`unsafe`、`stackalloc`、`GCHandle`或手工非托管内存。
- 不新增第三方依赖；不改变Quicker数据映射和变量写回方式。
- `_data`是Quicker数据映射的写回载体，`Window_Closed`中不得无条件清空或移除输出键；`_winContext`默认保留到宿主回收。清理只针对不与数据映射共享的会话缓存、执行队列和界面集合。

## 3. 总体修复架构

### 3.1 三层防线

```text
第一层：WindowSession
  └─ 所有异步任务携带会话；会话关闭后任何回调都不能碰UI/新状态

第二层：数据版本 + 不可变快照
  └─ 后台只读快照；结果回传时校验 session + DataVersion + 长度

第三层：资源所有权与失败复位
  └─ COM/Process/Dialog/Popup 成对释放；线程/队列失败必复位并提示
```

三层不能只做一层：只做会话，仍可能读可变数据；只做快照，旧线程仍可能写新缓存；只做释放，仍可能跨会话执行。

```csharp
private static WindowSession _session;

private static bool IsCurrent(WindowSession session)
{
    return session != null && !session.Closed && object.ReferenceEquals(session, _session);
}
```

```csharp
private static bool Post(WindowSession session, Action action)
{
    if (action == null || !IsCurrent(session))
        return false;
    return Post(session.Dispatcher, delegate()
    {
        if (!IsCurrent(session))
            return;
        try
        {
            action();
        }
        catch (Exception ex)
        {
            RefreshErrorBanner("后台结果应用失败：" + ex.Message);
        }
    });
}
```

关键规则：

1. 异步入口先捕获`WindowSession session = _session;`，后续只使用该局部变量。
2. Dispatcher回调先`IsCurrent(session)`，再检查`DataVersion`/代际。
3. `Window_Closed`只关闭当前会话，不重置旧会话的取消标志。
4. 会话对象通过引用计数或“最后一个回调自然释放”回收，不强制`GC.Collect`。

## 4. P0修复方案（下一稳定版必须完成）

### 4.1 P0-1 统一会话与执行会话隔离

#### 问题

- `ExecutionWorker`（`src/CustomWindow.Aux.cs:5354-5372`）读取静态`_execQueue`、`_execCursor`、`_execStop`。
- `PostExecutionCompleted`（`:5711-5734`）把`_execStop`置回`false`；`ResetRuntimeState`（`:420-505`）也会复位。
- 旧窗口的大文件复制未结束时重开窗口，旧线程可能领取新队列任务，造成重复执行或错行写入。

#### 目标

- 执行工作线程只捕自己的`ExecutionSession`，不读全局执行状态。
- 新窗口创建新会话；旧会话只取消，不复位。
- 所有执行回调校验会话身份；旧会话结果直接丢弃。

#### 代码改动

| 文件/位置 | 改动 |
|---|---|
| `CustomWindow.Aux.cs` 字段区 | 新增`WindowSession`、`ExecutionSession`；新增`_session` |
| `OnWindowCreated`/`OnWindowLoaded` | 创建会话并绑定`Dispatcher`、`Config`、`Files`、`Rows`、`HashCache` |
| `ResetRuntimeState` | 关闭旧会话；创建新会话；不再直接复位旧执行字段 |
| `Execute_Click` | 创建`ExecutionSession`，复制队列和配置快照；先把`Workers`设为计划数，再逐个启动线程，启动失败立即递减 |
| `ExecutionWorker` | 改为`ExecutionWorker(ExecutionSession session)`，循环条件用`session.Cancelled` |
| `ExecuteOneFile` | 接收`session`，执行配置从会话读取 |
| `ExecutionCancelCheck` | 改为按会话创建`Func<bool>`，不再读全局`_execStop` |
| `PostExecutionCompleted` | 改为`PostExecutionCompleted(ExecutionSession session)`，校验会话后再更新UI |
| `Window_Closing` | 只设置当前会话`Execution.Cancelled=true`，不写全局`_execStop`；保留“停止后关闭”状态机 |
| `Window_Closed` | 关闭会话；不重置旧会话标志 |

```csharp
private static void ExecutionWorker(object state)
{
    ExecutionSession session = (ExecutionSession)state;
    try
    {
        while (!session.Cancelled)
        {
            int index = Interlocked.Increment(ref session.Cursor) - 1;
            if (index >= session.Queue.Count)
                break;
            if (session.Cancelled)
                break;
            ExecuteOneFile(session, session.Queue[index]);
        }
    }
    finally
    {
        int remaining = Interlocked.Decrement(ref session.Workers);
        if (remaining == 0)
            PostExecutionCompleted(session);
    }
}
```

启动前把`Workers`设为计划数，而不是每成功启动一个才加一；否则第一个线程可能很快跑完并把计数减到0，导致主线程尚未启动完就误触发“执行完成”。

```csharp
private static bool TryStartThread(Thread thread, out Exception error)
{
    error = null;
    try
    {
        thread.Start();
        return true;
    }
    catch (Exception ex)
    {
        error = ex;
        return false;
    }
}
```

```csharp
private static void PostExecutionCompleted(ExecutionSession session)
{
    if (session == null || !IsCurrent(session.Owner))
        return;
    if (!object.ReferenceEquals(session.Owner.Execution, session))
        return;
    Post(session.Owner, delegate()
    {
        session.Owner.Execution = null;
        _executing = false;
        StopExecutionTimer();
        FlushExecutionUi();
        RefreshGridFilterIfActive();
        UpdateExecutionStatus();
        // 后续关闭/完成逻辑保持不变
    });
```

#### 失败与边界

- 线程启动失败：`Workers`按计划数预置，启动失败立即递减；若为0，立即复位`_executing=false`并显示错误。
- 部分线程启动失败：已启动线程继续消费同一队列；`Workers`的递减总数仍等于计划数，完成回调只触发一次。
- 关闭时旧线程仍在`CopyFileEx`：只标记`session.Cancelled=true`；旧线程完成当前文件后退出，不会领取新队列。
- `Window_Closing`保留“停止后关闭”状态机：第一次关闭请求只取消并提示，执行线程全部退出后由完成回调关闭窗口；若当前文件长时间不返回，二次确认才允许强制关闭。
- 强制关闭：旧线程可能继续当前文件操作，但不会触碰新会话；UI提示“当前文件操作可能继续完成”。

#### 测试与验收

| 测试 | 通过标准 |
|---|---|
| 大文件复制中关闭，立即重开并执行新队列 | 新队列只执行一次；旧线程不写新行；无重复重命名/复制 |
| 执行8路，关闭/重开20次 | 无线程数单调增长；无`_executing`卡死 |
| 注入`Thread.Start`失败 | 界面提示启动失败，按钮恢复可用 |
| 执行完成后再次执行 | 新会话从0开始，旧完成回调不影响新进度 |

### 4.2 P0-2 布局不可变快照与数据版本

#### 问题

- `ComputeLayouts`（`:2478-2513`）先读`_files.Count`，再按下标读`_files[index]`。
- `FinalizeLayouts`（`:2642-2737`）顺序读`_files[i]`。
- `ApplyLayouts`（`:2829-2862`）按当前`_files.Count`索引旧`layouts`。
- `ReplaceInputSelection`（`:3734-3797`）不递增`_recomputeGeneration`，不等待布局线程。新列表更长时，`ApplyLayouts`可抛`IndexOutOfRangeException`。

#### 目标

- 后台只读快照；结构变化生成新版本；旧结果因版本不匹配被丢弃。
- 任何数据替换都不需要“等旧布局线程读完”，从根本上消除竞争。

| 排序/筛选变化 | 不递增 | 允许复用布局，仅刷新视图 |

#### 测试与验收

| 测试 | 通过标准 |

### 4.3 P0-3 `_layoutWorkerCount`生命周期与超时

#### 问题

- 计数在`:2419`递增，在`:2433`和`:2444`递减；`ResetRuntimeState`和`Window_Closed`均未复位。

- 差异更新等待有上限；超时后作废旧布局并安排全量重算。

- `ApplySelectionDiff`发现`ActiveCount > 0`时，把差异放入`_pendingSelectionDiff`并启动150ms应用定时器。

- 每次`BeginLayout`必须对应一次`EndLayout`，用`try/finally`保证；诊断中断言计数不得为负。

### 4.4 P0-4 Explorer COM所有权与逐个释放

#### 问题

```csharp
private sealed class ComScope : IDisposable
{
    private readonly List<object> _owned = new List<object>();

    public T Track<T>(T value) where T : class
    {
        if (value != null && Marshal.IsComObject(value))
        {
            for (int i = 0; i < _owned.Count; i++)
            {
                if (object.ReferenceEquals(_owned[i], value))
                    return value;
            }
            _owned.Add(value);
        }
        return value;
    }

    public void Dispose()
    {
        for (int i = _owned.Count - 1; i >= 0; i--)
        {
            object value = _owned[i];
            _owned[i] = null;
            if (value == null || !Marshal.IsComObject(value))
                continue;
            try
            {
                Marshal.ReleaseComObject(value);
            }
            catch
            {
            }
        }
        _owned.Clear();
    }
}
```

### 4.5 P0-5 哈希缓存代际、文件身份与失效

#### 问题

## 5. P1修复方案（同版或紧随版本）

### 5.1 线程启动失败与计数复位

#### 范围

- `EnsureHashWorker`（`:2179-2250`）：先`_hashRunning=true`，后`Thread.Start()`无保护。
- `StartScanInternal`（`:1722-1890`）：工作线程启动失败，`workersRemaining`不递减，发布线程无限等待。
- `Execute_Click`（`:5320-5352`）：执行线程启动失败，`_execWorkers`不复位。

#### 措施

1. 复用P0-1引入的`TryStartThread(Thread thread, out Exception error)`统一包装`Start()`。
2. 计数规则统一：执行会话按“计划数预置、启动失败递减”；扫描/哈希记录实际启动数，失败不增加等待计数。
3. 扫描：`workerCount`改为实际启动数；若为0，发布线程直接结束并显示“扫描线程启动失败”；分块由已启动线程继续领取，不影响完整性。
4. 哈希：启动失败立即`_hashRunning=false`，恢复按钮，显示错误；不留下“计算中”。
5. 执行：`Workers`按计划数预置，启动失败立即递减；若为0，复位`_executing=false`，不进入执行态；部分失败继续执行。
6. 所有后台入口最外层`try/catch/finally`，`finally`保证递减/复位。

`TryStartThread`的定义见4.1节，不在P1重复实现。

#### 验收

- 注入`Thread.Start`异常：扫描/哈希/执行都能回到可操作状态，无永久“计算中/执行中”。
- 扫描部分线程失败：仍发布全部可读文件，状态提示实际线程数。

### 5.2 `RunIndexedParallel`超时、排队失败与异常上报

#### 问题

- `RunIndexedParallel`（`:2907-2954`）忽略`QueueUserWorkItem`返回值。
- `body`异常被空`catch`吞掉。
- `done.Wait()`无超时；网络/COM挂起时调用线程永久等待。
- 当前无超时，所以不存在`CountdownEvent`释放竞争；增加超时后必须处理晚`Signal`。

#### 措施

1. `CountdownEvent`初始化为计划工作项数`workerCount`；每个槽位无论排队成功还是内联执行，都必须且只能`Signal`一次。
2. `QueueUserWorkItem`返回`false`或抛异常时，当前线程内联执行该工作项；不允许出现“既不排队也不执行”的槽位。
3. `done.Wait(timeoutMs)`；超时设置`cancelled=1`，返回`false`，由调用方显示“计算超时”，并安排串行重试或放弃。`done.Wait`只允许在后台线程调用。
4. 工作项`body`异常写入`ConcurrentQueue<Exception>`；等待结束后汇总，交给调用方记录/提示，不静默吞掉。
5. 超时后不立即`Dispose`：先让已排队工作项检查`cancelled`并退出；`Signal`用`try/catch (ObjectDisposedException)`保护，或延迟释放到所有工作项退出。
6. 增加`[ThreadStatic] bool _insideParallelWorker`；工作项内调用哈希时禁止内层`Parallel.For`。

```csharp
CountdownEvent done = new CountdownEvent(workerCount);
for (int i = 0; i < workerCount; i++)
{
    try
    {
        if (!ThreadPool.QueueUserWorkItem(worker))
            worker(null); // 内联执行，worker的finally负责Signal
    }
    catch
    {
        worker(null);
    }
}
if (!done.Wait(timeoutMs))
{
    Interlocked.Exchange(ref cancelled, 1);
    // 不立刻Dispose；返回超时，让调用方决定回退
}
```

#### 验收

- 注入队列失败：任务仍完成或明确回退串行。
- 注入慢任务：超时返回，UI不永久冻结。
- 注入`body`异常：错误被记录/提示，不被静默吞掉。

### 5.3 幂等`ShutdownSession()`与完整清理

#### 问题

`Window_Closed`（`:6049-6164`）停止主要定时器和线程，但遗留`_layoutWorkerCount`、`_execQueue`、`_execDirs`、`_lastCaret`、`_scanning`、`_previewDirty`、`_presetPopup`等；且无`try/finally`。`_data`/`_winContext`是宿主写回与上下文对象，按1.4节约束保留，不按普通缓存清理。

#### 措施

新增`ShutdownSession(WindowSession session)`，按固定顺序执行，每步独立`try/catch`，整体`try/finally`：

```text
1. session.Closed = true; session.CancelRequested = true
2. 停止所有DispatcherTimer并置空
3. 取消执行/扫描/哈希/布局/选择读取
4. 关闭Popup、错误横幅、进度条
5. 释放COM/Process/Dialog/文件流
6. 清空会话Rows/Files/Paths/HashCache/ExecDirs/LastCaret；保留Data输出字典与WinContext
7. 解除事件、清空DataGrid ItemsSource
8. 最后置空Window/Config/Session
```

要求：

- `Window_Closed`入口先捕获`WindowSession session = _session;`，后续只用该局部变量；即使新窗口已创建，也不能关闭新会话。
- 可重复调用；第二次直接返回。
- 不等待网络IO无限期；线程等待使用短超时（如2秒），超时记录并继续清理。
- 先`IsOpen=false`再置空Popup。
- `Rows`/`Files`若被`_data`输出引用，不能原地`Clear()`；改为替换会话引用、解绑`ItemsSource`，避免清空宿主待写回的列表。
- 清理后新窗口从全新会话开始，不继承任何旧计数/旧集合。

#### 验收

- 连续开关100次，句柄/线程/私有内存不单调增长。
- 关闭时任一清理步骤抛异常，后续步骤仍执行。
- 重开后实时获取、哈希、执行均正常。

### 5.4 UI线程禁止同步布局/比较/哈希

#### 问题

`RecomputeAll(true)`用于执行前、预设载入等场景，可能在UI线程执行`FinalizeLayouts`→`TryCompareFileContent`→`ComputeHashHex`；大文件/网络文件会冻结界面。

#### 措施

1. `RecomputeAll`只负责发起异步布局；同步重载改为“异步+完成回调”。
2. 执行前若布局未就绪：禁用【执行】，显示“正在计算目标路径…”，布局完成后自动继续；用户可取消。
3. 预设载入后异步重算，不阻塞UI。
4. 哈希缓存已齐但仍有“计算中”行时，调用`RecomputeAll(false)`而不是`true`。
5. 内容比较、哈希、`FileInfo`批量读取全部在后台线程。
6. `ApplyLayouts`分批应用（P2），P1先保证不在UI线程做IO。

#### 验收

- 1000行、含大文件比较时，点击执行不再出现长时间无响应。
- 布局中可取消、可关闭窗口。

### 5.5 全局并发预算与嵌套并行

#### 问题

扫描4~12、哈希1、布局8、比较8、执行1~8、BLAKE3最多8，理论上可同时数十个CPU/IO线程；`RunIndexedParallel`工作项内再调用BLAKE3`Parallel.For`，形成线程池任务等待线程池任务。

#### 措施

1. 新增`ComputeBudget`：按`Environment.ProcessorCount`分配重计算令牌，默认`max(1, ProcessorCount / 2)`，上限8。
2. `TryAcquire()`非阻塞；拿不到令牌时哈希走串行，不排队等待。
3. `[ThreadStatic] bool _insideParallelWorker`：已在布局/执行工作项内时，BLAKE3不再`Parallel.For`。
4. 执行后校验与后台哈希共享预算；执行8路时自动降低校验并行。
5. 网络路径按主机限流（P2）：同一UNC主机最多2~4个并发。
6. 所有令牌`finally`释放；会话关闭后不再获取。

#### 验收

- 1000行+哈希+执行组合下，CPU不持续100%、线程数不持续上升。
- 大文件BLAKE3吞吐不明显低于0.06.21基线（允许±10%）。

### 5.6 哈希读取共享模式与一致性

- `ComputeHashHex`使用`FileShare.ReadWrite | FileShare.Delete`。
- 读取前后比较`Length`、`LastWriteTimeUtc`；变化则重算一次，仍变化标记“文件变化中”。
- 执行前若哈希任务仍在运行，优先等待/取消；无法等待时按共享冲突重试。
- 缓存写入使用读取后的身份，不使用读取前的旧身份。

### 5.7 Process、Dialog、Popup释放

| 资源 | 措施 |
|---|---|
| `TryGetProcessCpuTime` | `using (Process p = Process.GetCurrentProcess())`；或缓存进程句柄，窗口关闭释放 |
| `BrowseForRoot` | `using (FolderBrowserDialog dialog = new FolderBrowserDialog())` |
| `_presetPopup` | `ShutdownSession`中`IsOpen=false`；清空`ItemsSource`；解除事件 |
| `_headerFilterPopup` | 已有`IsOpen=false`，纳入统一关闭步骤 |
| 文件流 | 全部`using`；异常路径也释放 |

### 5.8 选择读取STA线程消息泵、超时与Join

#### 问题

`SelectionReaderLoop`（`:3468-3511`）在STA线程直接做Shell晚绑定COM，无消息泵；`StopSelectionReader`不Join；快速重开可能短暂存在多个STA线程。

#### 措施

1. 选择读取线程改为“STA + `Dispatcher`消息泵”：

```csharp
Thread thread = new Thread(delegate()
{
    Dispatcher dispatcher = Dispatcher.CurrentDispatcher;
    _selectionReaderDispatcher = dispatcher;
    dispatcher.BeginInvoke(new Action(delegate()
    {
        // 读取请求循环
    }));
    Dispatcher.Run();
});
thread.SetApartmentState(ApartmentState.STA);
thread.IsBackground = true;
thread.Start();
```

2. 请求通过`dispatcher.BeginInvoke`投递，只保留最新请求ID；旧请求直接丢弃。
3. `StopSelectionReader`：设置停止标志；`dispatcher.BeginInvokeShutdown`；`Join(2000)`。
4. 若2秒未退出：不再启动新线程，显示“选择读取线程未退出，实时获取已暂停”；避免线程累积。
5. Shell实例在STA线程内缓存；线程退出时释放。
6. 每次读取有超时监控；超时后返回空并记录，不阻塞UI。

## 11. 团队结论与实施建议

### 11.1 架构组

同意按“会话→快照→资源→性能”分层修复。P0-1/2/3必须同批完成，不能只修计数或只加锁；否则旧线程仍可能读可变数据。

### 11.2 前端（WPF/UI）组

同意UI线程只做应用结果和渲染。需要新增“计算中/停止中/启动失败/超时”状态，保证按钮禁用与恢复一致；`ApplyLayouts`分批刷新在P2实施。

### 11.3 后端（核心/文件引擎）组

同意哈希缓存改为文件身份键，读取使用`FileShare.Delete`并做前后一致性校验；执行后按路径失效缓存。BLAKE3并行需服从全局预算与嵌套标志。

### 11.4 性能组

同意先消除嵌套并行和UI线程IO，再谈缓冲调优。P0/P1阶段以“不退化”为目标；P2再用基准决定BLAKE3缓冲和Shell缓存策略。

### 11.5 并发组

同意执行会话与布局快照是根因修复；`volatile`只能解决可见性，不能替代会话/版本。`CountdownEvent`超时后不得立即释放，必须处理晚`Signal`。

### 11.6 开发组

同意按PR-01至PR-10小步实施，每个PR独立可回滚；不夹带功能改动；每步更新测试与CHANGELOG。

### 11.7 测试组

同意以“布局中重新获取、执行中关闭再打开、快速选择1000次、网络断网”为P0准入场景；增加故障注入与资源长跑；实机基线由测试组出具。

## 12. 结论

本方案以最小行为变更换取生命周期安全：先让所有异步任务拥有明确会话，再让后台只读快照，再让资源有明确所有者，最后优化并发预算与UI体验。P0完成前，当前版本不应作为Quicker长期驻留进程的稳定版交付；P0/P1完成后，再以Windows实机资源和压力测试决定是否进入P2优化。

## 13. 特别说明

特别说明（0.01）：本方案不修改代码，只给出实施与验收依据。评审报告中“哈希缓存属于高风险扩大项”的表述已在需求文档0.0.36中更正：哈希缓存属于低风险正确性扩展，4项高风险为执行会话、布局计数、COM释放、布局数据并发；该更正不改变P0/P1/P2排序与验收要求。评审报告将`_data`/`_winContext`列为关闭后残留，本方案按Quicker数据映射写回约束保留它们；可清理的是会话缓存、执行队列、界面集合和Popup，不把宿主写回载体当作泄漏对象。
