# 批量重命名器 线程安全与内存安全分析

> 版本：0.01

## 1. 分析范围与方法

- 对象：`src/CustomWindow.Aux.cs`、`src/RenamerCore.cs`、`src/CustomWindow.xaml` 及交付生成代码。
- 方法：静态代码审查、线程/句柄/静态状态清单、异常路径与生命周期推演。
- 限制：当前环境无法运行 Windows/Quicker/WPF 实机，未做动态句柄计数、COM 引用计数和长时间稳定性测试；结论为代码级风险判断，需在 Windows/Quicker 实机复核。

## 2. 结论摘要

本项目没有 `unsafe`、指针、`stackalloc` 或手工内存分配，数组访问有运行时边界检查，**不存在传统意义上的缓冲区溢出、悬垂指针或直接内存破坏**。主要风险集中在四类：

1. **非托管资源生命周期**：资源管理器 COM 对象未逐个释放、`Process.GetCurrentProcess()` 未释放、`FolderBrowserDialog` 未释放。
2. **静态状态跨窗口会话残留**：`_data`、`_winContext`、`_lastCaret`、`_execQueue`、`_execDirs`、`_layoutWorkerCount` 等未在关闭时完整清理。
3. **执行线程跨会话**：执行线程只依赖全局 `_execStop`，没有会话标识；旧窗口的执行线程可能读到新窗口的 `_execQueue` 和计数器。
4. **布局线程与UI行数据竞争**：后台布局读取 `_files`/行词典时，手动重取、日期刷新或新扫描可能同时替换/修改这些数据。

| 等级 | 问题 | 后果 |
|---|---|---|
| 高 | 执行线程跨会话共享 `_execQueue`/计数器 | 旧任务误执行新队列、进度错乱、重复执行或提前“完成” |
| 高 | `_layoutWorkerCount` 未在重置/关闭时复位 | 实时差异更新可能永久被延迟，150ms定时器持续空转 |
| 高 | 资源管理器 COM 对象未逐个释放 | RCW/COM引用累积，内存和句柄增长，Explorer交互变慢 |
| 高 | 布局线程与 `_files`/行词典并发读写 | 布局错误、索引异常、UI回调异常；极端情况进程退出 |
| 中 | `_data`/`_winContext`/`_lastCaret`/`_execQueue` 未清空 | 关闭后仍持有窗口上下文、编辑器文档、全部执行行 |
| 中 | 网络/云端IO无超时，扫描/哈希/执行线程可能挂起 | 遗留线程累积；执行中关闭窗口可能长时间无响应 |
| 中 | `RunIndexedParallel` 的 `done.Wait()` 无超时且忽略排队失败 | 线程池异常/关闭时可能永久等待，UI冻结 |
| 中 | BLAKE3 `Parallel.For` 嵌套在布局线程池任务中 | 线程池饥饿、过度并行、UI变慢 |
| 中 | 选择读取STA线程无消息泵 | Shell COM调用存在挂起/死锁风险 |
| 低 | `Process.GetCurrentProcess()` 未Dispose | 进程句柄短时增长，依赖GC回收 |
| 低 | `FolderBrowserDialog` 未Dispose、`_presetPopup` 未关闭 | 少量非托管句柄/弹窗残留 |
| 低 | 多实例共用全部静态字段 | 同时打开两个同动作窗口会互相覆盖状态 |

## 3. 线程、定时器与非托管资源清单

### 3.1 线程

| 线程/机制 | 创建位置 | 是否后台 | 取消方式 | 是否Join | 主要风险 |
|---|---|---|---|---|---|
| 扫描工作线程（最多12） | `StartScanInternal` `src/CustomWindow.Aux.cs:1775` | 是 | `_scanGeneration` | 否 | 单个 `FileInfo`/EXIF/网络IO可长时间挂起 |
| 扫描发布线程 | `src/CustomWindow.Aux.cs:1835` | 是 | `_scanGeneration` | 否 | 发布线程异常死亡后UI停在“读取中”，无泄漏但卡死 |
| 哈希工作线程 | `EnsureHashWorker` `src/CustomWindow.Aux.cs:2244` | 是 | `_hashStop`/`_hashGeneration` | 否 | 只在文件之间检查取消，大文件/网络文件不可中断 |
| 布局工作线程 | `RecomputeAll` `src/CustomWindow.Aux.cs:2420` | 是 | `_recomputeGeneration` | 否 | `_layoutWorkerCount` 可能永久不归零 |
| 资源管理器选择读取线程 | `EnsureSelectionReader` `src/CustomWindow.Aux.cs:3440` | 是 | `_selectionReaderStop`/请求号/线程身份 | 否 | STA无消息泵；COM调用挂起时线程遗留 |
| 执行工作线程（1~N） | `Execute_Click` `src/CustomWindow.Aux.cs:5348` | 是 | `_execStop` | 否 | 无会话标识；旧线程可跨窗口会话继续运行 |
| `RunIndexedParallel` 线程池任务 | `src/CustomWindow.Aux.cs:2950` | 是（线程池） | 无 | `done.Wait()` | 排队失败/异常时永久等待；UI线程可被阻塞 |
| BLAKE3 `Parallel.For` | `src/RenamerCore.cs:1823` | 是（线程池） | 无 | 调用线程等待 | 嵌套并行导致线程池饥饿；UI线程调用时冻结UI |
| WinEvent钩子回调 | `SetWinEventHook` | 系统投递到安装线程 | `UnhookWinEvent` | 不适用 | 未执行清理时钩子保留到进程退出 |

所有显式 `Thread` 均设置 `IsBackground=true`，因此**进程正常退出不会被这些线程阻塞**。但 Quicker 是长期驻留进程，窗口关闭后线程若因IO/COM挂起，仍会占用线程、栈和非托管资源。

### 3.2 定时器

`DispatcherTimer`：`_debounceTimer`、`_gridFilterTimer`、`_selectionDebounceTimer`、`_selectionFallbackTimer`、`_selectionGuardTimer`、`_selectionApplyTimer`、`_hashResumeTimer`、`_layoutDeferTimer`、`_execTimer`。

- `Window_Closed` 通过 `RemoveSelectionHook` 停止选择相关定时器，并停止 `_debounceTimer`、`_gridFilterTimer`、`_hashResumeTimer`、`_layoutDeferTimer`、`_execTimer`，随后把字段置空。
- `_selectionApplyTimer` 在 `_layoutWorkerCount>0` 时会每150ms重启，直到计数归零；计数卡死时该定时器会一直空转。
- 若 `Window_Closed` 中途抛异常，后续定时器停止与字段清理不会执行，定时器会继续持有Dispatcher和闭包。

### 3.3 非托管句柄/资源

| 资源 | 位置 | 释放情况 | 风险 |
|---|---|---|---|
| WinEvent钩子 | `InstallSelectionHook`/`RemoveSelectionHook` | `UnhookWinEvent` | 正常关闭释放；异常退出由OS回收 |
| Shell.Application COM | `GetExplorerSelectedPaths` | `finally` 释放 `shell`、`windows` | 子对象未释放，见5.1 |
| Explorer窗口/文档/选中项 COM | `CollectWindowSelection` | **未释放** | RCW累积，高风险 |
| 文件流 | 哈希、比较、复制、EXIF | `using` 或手动 `Dispose` | 正常路径已释放 |
| `HashAlgorithm` | MD5/SHA-256 | `using` | 正常 |
| `Process` | `TryGetProcessCpuTime` | **未Dispose** | 进程句柄短时增长 |
| `FolderBrowserDialog` | `BrowseForRoot` | **未Dispose** | 少量对话框资源残留 |
| `CountdownEvent` | `RunIndexedParallel` | `using` | 正常；中断时可能提前Dispose |
| WPF `Popup` | `_headerFilterPopup`/`_presetPopup` | 头部弹窗关闭；预设弹窗关闭时未显式 `IsOpen=false` | 可能残留弹窗窗口/视觉树 |
| `BitmapDecoder`/`BitmapFrame` | `TryReadExifDate` | 局部对象，FileStream已Dispose | 正常路径无长期句柄 |

## 4. 线程安全问题

### 4.1 布局线程与 `_files`/行词典并发（高）

证据：

- `ComputeLayouts` 读取 `_files.Count` 并在工作线程执行 `_files[index]`：`src/CustomWindow.Aux.cs:2478-2513`。
- `FinalizeLayouts` 在工作线程读取 `_files[i]["SourcePath"]`：`src/CustomWindow.Aux.cs:2642-2737`。
- `ApplyLayouts` 在UI线程按 `_files.Count` 访问 `layouts[i]`：`src/CustomWindow.Aux.cs:2829-2860`。
- `ReplaceInputSelection` 直接把 `_files` 替换为新列表，**没有检查 `_layoutWorkerCount`，也没有在替换前递增 `_recomputeGeneration`**：`src/CustomWindow.Aux.cs:3734-3795`。`_recomputeGeneration` 直到 `StartScanInternal` 才递增（`src/CustomWindow.Aux.cs:1726`）。
- `RefreshDates` 先递增 `_recomputeGeneration`，随后直接修改每一行的日期字段：`src/CustomWindow.Aux.cs:1590-1610`；后台布局线程可能仍在读取同一行词典。
- `AddFileBatch` 在UI线程向 `_files`/`_rows` 追加：`src/CustomWindow.Aux.cs:1892-1925`；若新扫描在旧布局线程未结束时启动，会与布局读取并发。

影响：

- `List<T>`/`Dictionary<TKey,TValue>` 不是线程安全容器；并发读写可能抛 `InvalidOperationException`、`ArgumentOutOfRangeException`，或读到不一致的行数据。
- 旧布局回调若在新 `_files` 上执行，`layouts` 长度与新 `_files.Count` 不一致时，`ApplyLayouts` 可能索引越界；该异常发生在UI Dispatcher 回调中，默认会终止进程（除非 Quicker 有全局异常处理）。
- 即使不崩溃，也可能把旧布局结果应用到新行，产生错误的目标路径或冲突序号。

`ApplySelectionDiff` 已经通过 `_layoutWorkerCount>0` 延迟修改（`src/CustomWindow.Aux.cs:3847`），但 `ReplaceInputSelection`、`RefreshDates` 和扫描启动路径没有同等保护，保护不完整。

### 4.2 执行线程跨会话生命周期（高）

证据：

- `_execQueue` 是静态字段：`src/CustomWindow.Aux.cs:206`；执行开始时赋值为本次队列：`src/CustomWindow.Aux.cs:5325`；工作线程循环读取静态 `_execQueue.Count` 和 `_execQueue[index]`：`src/CustomWindow.Aux.cs:5354-5364`。
- 工作线程只检查 `_execStop`，没有会话号/代际号。
- `Window_Closed` 设置 `_execStop=true`、`_executing=false`，但**不等待执行线程结束，也不清空 `_execQueue`/`_execWorkers`**：`src/CustomWindow.Aux.cs:6049-6164`。
- 下一次 `OnWindowLoaded` 的 `ResetRuntimeState` 会把 `_execStop=false`、`_execWorkers=0`、`_execQueue=new`、`_execCursor=0`：`src/CustomWindow.Aux.cs:480-495`。

影响：

- 如果上一个窗口的执行线程仍在长耗时复制/网络IO中，用户打开新窗口并开始新执行，旧线程会在新会话中看到 `_execStop=false`，继续从新 `_execQueue` 取任务，造成**重复执行/越权执行**。
- 旧线程会修改新会话的 `_execCursor`、`_execDone`、`_execErrors`、`_execWorkers`，导致新执行进度错乱；旧线程的 `finally` 递减 `_execWorkers`，可能让新会话提前触发“执行完成”。
- 旧线程的 `ReportExecutionRow` 可能向新窗口 Dispatcher 投递旧行更新（旧行不在新 `_rows` 中，通常不可见，但会消耗UI消息）。

这是目前最严重的跨会话线程安全缺陷。

### 4.3 `_layoutWorkerCount` 卡死（高）

证据：

- `_layoutWorkerCount` 在异步布局启动时 `Interlocked.Increment`：`src/CustomWindow.Aux.cs:2419`；在 Dispatcher 回调中递减：`src/CustomWindow.Aux.cs:2433`；`Post` 失败时递减：`src/CustomWindow.Aux.cs:2444`。
- `ResetRuntimeState` 与 `Window_Closed` 都**没有**把它复位：`src/CustomWindow.Aux.cs:420-505`、`6049-6164`。
- `ApplySelectionDiff` 在计数>0时保存待处理差异并返回：`src/CustomWindow.Aux.cs:3847-3855`；`EnsureSelectionApplyTimer` 每150ms检查，计数>0就重启：`src/CustomWindow.Aux.cs:3960-3980`。

影响：

- 布局线程因网络IO挂起、`Thread.Start` 失败、Dispatcher 关闭导致回调未执行时，计数永远>0。
- 新窗口会话中，实时获取的差异更新会永久进入“待处理”状态，列表不再更新；150ms定时器持续空转。
- 手动【重新获取选择的文件】走 `ReplaceInputSelection`，不受该计数限制，因此表现为“手动可用、实时失效”，更难定位。

### 4.4 多实例静态状态（中高）

`_window`、`_grid`、`_editor`、所有定时器、所有工作线程字段均为静态。`Window_Closed` 通过 `closedWindow != _window` 忽略非当前窗口的关闭：`src/CustomWindow.Aux.cs:6051-6053`。

如果 Quicker 允许同一动作同时打开两个自定义窗口：

- 第二个窗口的 `OnWindowLoaded` 会覆盖第一个窗口的全部静态引用。
- 第一个窗口关闭时直接 return，不会清理；它的定时器/钩子/线程是共享的，状态归属混乱。
- 第二个窗口关闭时清理的是第二套控件；第一个窗口的视觉树可能已无静态引用，但 `_data`/`_winContext` 等仍可能持有。

若产品明确“同一时间只允许一个窗口”，应在代码/文档中声明；否则需要把窗口状态改为实例字段或按窗口ID隔离。

### 4.5 跨线程可见性（低中）

以下字段被工作线程/事件线程读取，但不是 `volatile`，也不是每次通过 `Volatile.Read`：

- `_executing`：WinEvent回调、选择读取结果判断。
- `_window`：WinEvent回调、选择读取线程、执行线程（先用 null 检查，再访问 Dispatcher）。
- `_selectionHook`：WinEvent回调。
- `_scanPerfWorkerCount`、`_scanPerfPathCount`、`_scanPerfStartTicks` 等性能字段：发布线程读取。

多数场景有 `BeginInvoke`、`lock` 或线程启动的 happens-before 关系兜底，实际危害有限；但在弱内存模型/极端时序下可能读到旧值，导致“执行中仍触发选择刷新”或多算一次性能文本。建议统一用 `volatile`/`Volatile.Read`。

### 4.6 `RunIndexedParallel` 等待与嵌套并行（中）

证据：`src/CustomWindow.Aux.cs:2907-2954`。

- `ThreadPool.QueueUserWorkItem` 的返回值未检查；若某个任务未成功排队，`done.Signal()` 少一次，`done.Wait()` 永久阻塞。
- `done.Wait()` 无超时；调用方可能是UI线程（同步布局路径），会造成UI冻结。
- `FinalizeLayouts` 的工作线程会调用 `TryCompareFileContent` → `ComputeHashHex` → BLAKE3 `Parallel.For`；外层是线程池任务，内层再向线程池排队，存在线程池饥饿/过度并行风险。
- `CountdownEvent` 在 `using` 中；若 `Wait()` 被 `ThreadInterruptedException` 中断，`Dispose` 后仍在运行的池线程调用 `Signal()` 会抛 `ObjectDisposedException`。

### 4.7 选择读取STA线程无消息泵（中）

`EnsureSelectionReader` 创建 `ApartmentState.STA` 线程：`src/CustomWindow.Aux.cs:3440`；`SelectionReaderLoop` 使用 `Monitor.Wait` 等待请求：`src/CustomWindow.Aux.cs:3468-3515`，没有 `Dispatcher.Run`/`Application.Run` 消息循环。

Shell.Application 的晚绑定调用通常能在专用STA线程同步完成，但部分 Shell COM 操作依赖公寓消息泵；没有消息泵时可能挂起或死锁。线程是后台线程，不会阻止进程退出，但会一直占用STA公寓和COM引用；`StopSelectionReader` 无法中断已进入的COM调用。

### 4.8 扫描/哈希/执行取消粒度（中）

- 扫描线程只在分块/文件之间检查 `_scanGeneration`；`FileInfo`、`Directory.Exists`、EXIF `BitmapDecoder` 对网络/云端路径可能长时间阻塞。
- 哈希线程只在文件之间检查 `_hashStop`；一个超大文件或网络文件的 BLAKE3 计算中途不可取消。
- 执行线程的 `CopyFileEx` 取消依赖进度回调；网络挂起时回调可能长时间不触发；`File.Move`/`File.Delete` 也无法取消。
- 每次新扫描/哈希可能新建线程，旧线程在IO返回前不会退出；在坏网络路径下可能累积多批遗留线程。

### 4.9 容器线程安全小结

- `_files`/`_rows`/`_paths`/`_loadedPaths`：设计上归UI线程；扫描工作线程只写自己的分块结果，发布线程通过 Dispatcher 追加，设计正确；但4.1的布局/手动刷新路径破坏了该约束。
- `_hashCache`：所有访问在 `_hashLock` 内，线程安全。
- `_execDirs`：所有访问在 `_execDirLock` 内，线程安全。
- `_crc32Table`：双重检查锁，线程安全。
- `_blake3*` 线程静态缓冲区：每线程独立；`Parallel.For` 只写 `cvs` 的不相交区间，线程安全。
- `_compareBufferA/B`：线程静态，线程安全。
- `_templateHashCheckKey/Value`：仅UI线程使用，安全。
- `_execQueue`：启动后只读，但跨会话被替换导致4.2。

## 5. 内存与句柄泄漏

### 5.1 资源管理器 COM 对象未释放（高）

证据：

- `GetExplorerSelectedPaths` 在 `finally` 只释放 `windows` 和 `shell`：`src/CustomWindow.Aux.cs:3565-3614`。
- `GetComItems(windows)` 返回的每个窗口 RCW 没有释放。
- `CollectWindowSelection` 取得 `Document`、`SelectedItems` 和每个选中项 RCW，但函数内没有任何 `ReleaseComObject`：`src/CustomWindow.Aux.cs:3618-3644`。
- 现有 `ReleaseComObject` 辅助方法只被用于 `windows`/`shell`：`src/CustomWindow.Aux.cs:3721-3731`。

影响：

- 每次实时选择读取都会留下多个 RCW（窗口、Document、SelectedItems、每个选中项）。RCW 最终由 GC 终结器释放，但实时获取可能每350ms触发一次；在 GC 前 RCW/COM 引用会快速累积。
- 这些 COM 对象通常持有 Explorer 的文档/选中项，可能让 Explorer 对象生命周期延长，增加内存和句柄压力，甚至影响 Explorer 响应。
- STA 线程没有消息泵时，RCW 终结器在 finalizer 线程跨公寓释放，存在挂起风险。

### 5.2 关闭后静态引用残留（中高）

`Window_Closed`（`src/CustomWindow.Aux.cs:6049-6164`）已清理大部分控件、集合和定时器，但以下引用未清理：

| 字段 | 行号 | 后果 |
|---|---|---|
| `_data` | 42、300/328 | 持有 Quicker 数据上下文、`files` 列表、输出列表、预设字典；大量文件时显著占用内存 |
| `_winContext` | 43、301/329 | 可能持有窗口/动作上下文，进而持有视觉树 |
| `_lastCaret` | 180、5876等 | `TextPointer` 持有 FlowDocument，文档及其 InlineUIContainer 被保留 |
| `_execQueue` | 206、5325 | 持有最后一次执行的全部行词典；直到下次 `ResetRuntimeState` 才替换 |
| `_execDirs` | 212 | 只在下次执行开始时 `Clear`（5321），关闭后保留所有目录字符串 |
| `_layoutWorkerCount` | 88 | 见4.3，不只是内存，还是功能卡死 |
| `_templateHashCheckKey` | 175 | 保留最后一次模板字符串，量小 |
| `_presetPopup` | 127 | 只置 null，没有 `IsOpen=false`；可能残留 Popup 窗口/视觉树 |

`ResetRuntimeState` 会清理其中一部分（`_lastCaret`、`_hashCache`、`_execQueue`、`_execDirs` 中的 `_execQueue` 是替换），但 `_data`/`_winContext` 被新值覆盖、`_execDirs` 不清、`_layoutWorkerCount` 不清；如果用户关闭窗口后不再打开，残留会持续到 Quicker 进程退出。

### 5.3 `Process.GetCurrentProcess()` 未释放（中）

`TryGetProcessCpuTime`：`src/CustomWindow.Aux.cs:2956-2968`：

```csharp
value = Process.GetCurrentProcess().TotalProcessorTime;
```

`Process` 持有当前进程句柄，未 `Dispose`，依赖终结器。扫描开始、布局上下文创建、性能文本生成都会调用；大量扫描/重算时句柄数会短时增长。修复：`using (Process p = Process.GetCurrentProcess()) { ... }`。

### 5.4 `FolderBrowserDialog` 未释放（低）

`BrowseForRoot`：`src/CustomWindow.Aux.cs:3380-3402` 直接 `new FolderBrowserDialog()`，未 `using`/`Dispose`。每次选择根目录会留下一个待终结的 `CommonDialog`，量小但应修复。

### 5.5 `_hashCache` 会话内增长（中低）

`_hashCache` 以 `路径|算法` 为键，只增不删：`src/CustomWindow.Aux.cs:146`、`2205-2216`。窗口关闭/重置会换新字典，但单次会话内如果实时选择遍历大量文件，缓存会持续增长（每项包含路径字符串、算法和哈希字符串）。不是永久泄漏，但可能达到数十MB。建议增加容量上限/LRU，或在删除行时按引用计数清理。

### 5.6 线程静态缓冲区（低，边界可控）

- `_blake3ReadBuffer` 最大1MB/调用线程；`_blake3CvBatch` 最大约32KB；`_blake3Block`/栈等约数KB。
- `_compareBufferA/B` 每线程约160KB。
- 这些缓冲区随线程存活；线程池线程长期存活时会保留，属于“有界内存驻留”，不是无限泄漏。若大量线程池线程执行过BLAKE3/冲突比较，可能累积数MB到数十MB。

### 5.7 定时器/钩子/弹窗（低中）

- 定时器在正常关闭路径均停止；异常关闭路径可能残留。
- WinEvent钩子在正常关闭路径 `UnhookWinEvent`；异常关闭路径保留到进程退出。
- `_presetPopup` 未显式关闭。

## 6. 异常退出与角落场景

### 6.1 进程被强制结束

- OS回收所有线程、句柄、COM代理和内存；不存在跨进程的持久泄漏。
- 所有显式线程均为后台线程，不会阻止进程结束。
- 文件复制到一半可能留下临时文件/半成品目标；这是数据一致性问题，不是内存泄漏。代码已有临时文件清理和重试，但强制结束无法保证。

### 6.2 UI线程未处理异常

- WPF/Quicker 默认可能终止进程；OS回收资源。
- 若 Quicker 捕获异常并保持进程存活，`Window_Closed` 可能未执行：定时器、WinEvent钩子、静态引用、后台线程都可能残留；下一次 `OnWindowLoaded` 的 `ResetRuntimeState` 只能清理一部分（`_layoutWorkerCount`、`_execDirs`、`_data`/`_winContext` 等仍可能残留旧值）。
- 建议在 `Window_Closed` 使用 `try/finally`，并让 `ResetRuntimeState` 无条件复位所有会话级静态字段。

### 6.3 后台线程未处理异常

- .NET Framework 默认：任意线程未处理异常会终止进程；`finally` 会执行，OS回收。
- 若宿主设置了全局异常处理并让进程继续，线程死亡后：
  - 扫描发布线程死亡 → 扫描不再发布/完成，`_scanning` 可能保持 true。
  - 哈希线程死亡 → `_hashRunning` 可能保持 true（`finally` 只在 generation 匹配时清），后续同算法哈希被跳过。
  - 执行线程死亡 → `ExecutionWorker` 的 `finally` 会递减 `_execWorkers`；若计数归零会触发完成；但若异常发生在 `finally` 之前未捕获，进程通常已退出。
- 代码已对多数 worker 主体做 try/catch/finally，风险主要集中在“线程死亡但进程被宿主保住”的场景。

### 6.4 `Window_Closed` 清理中途异常

- 若 `Window_Closed` 中途抛异常，后续字段/定时器/钩子不会清理。
- 已排队的 `DispatcherTimer` Tick 可能在 `Stop()` 之后仍执行一次：`DebounceTimer_Tick`（`src/CustomWindow.Aux.cs:1477-1482`）没有检查 `_window`/`_config`，关闭后调用 `ApplyUiConfig` 可能空引用；`_gridFilterTimer`/`_execTimer`/选择相关 Tick 有 null 检查。
- 建议整个清理体包在 `try/finally`，把最关键的资源释放（钩子、线程停止、定时器停止、静态引用清空）放在 `finally`；并让 `DebounceTimer_Tick`/`ApplyUiConfig` 在 `_window==null || _config==null` 时直接返回。

### 6.5 `OnWindowLoaded`/`FindControls` 异常

- `FindControls` 依赖 `FindName` 返回非空；若 XAML 与代码不一致，后续 `AttachEvents` 会空引用。
- `ResetRuntimeState` 可能未执行或执行到一半，静态状态处于半初始化；下一次打开可能继承脏状态。
- 这是部署/版本不一致问题，不是内存泄漏，但会放大上述静态状态问题。

### 6.6 线程启动/线程池排队失败

- `StartScanInternal` 若某个 `Thread.Start` 抛异常，`workersRemaining` 初始为 `workerCount`，失败线程不会递减，发布线程会一直等待。
- `ExecutionWorker` 若某个 `Thread.Start` 失败，`_execWorkers` 初始为 `parallel`，少一个递减，执行永远不会完成。
- `RunIndexedParallel` 若 `QueueUserWorkItem` 返回 false，`done` 永远不会归零，`done.Wait()` 永久阻塞。
- 这些属于低概率但明确的死锁/卡死角落。

### 6.7 网络/云端路径

- `FileInfo.Exists`、`Length`、`CreationTime`、`LastWriteTime`、`Attributes`、EXIF `FileStream`、BLAKE3、`CopyFileEx`、`File.Move/Delete` 都可能长时间阻塞。
- 每次实时选择变化都会取消旧扫描并启动新扫描；旧线程在IO返回前无法退出，可能累积多批“遗留线程”。
- 执行中关闭窗口时，`Window_Closing` 会先弹确认，然后设置 `_execStop` 并等待执行完成再关闭；若IO挂起，用户可能长时间无法关闭窗口。
- 当前没有超时/强制取消机制；这是“线程无法销毁”的主要现实来源。

### 6.8 多实例/重复打开

- 见4.4；静态字段是单实例假设，重复打开会互相覆盖。
- `Window_Closed` 的窗口身份检查会跳过旧窗口的清理，造成清理责任错位。

## 7. 已有的安全设计（值得保留）

- 所有显式线程 `IsBackground=true`，进程退出不被阻塞。
- 扫描/哈希/布局使用代际号取消旧任务；工作线程只写自己的结果槽位。
- `_layoutWorkerCount`、`_execWorkers`、`_hashDone` 等使用 `Interlocked`。
- `_hashCache`、`_crc32Table`、`_execDirs` 有锁保护。
- 文件流/哈希算法大多使用 `using`；`CopyFileManaged` 手动 `Dispose`。
- `CopyFileEx` 的 `CopyProgressRoutine` 委托在同步调用期间保持存活；WinEvent 委托保存在静态字段，避免被GC回收。
- `Post`、选择读取、执行行更新等 Dispatcher 调用有 try/catch 或 null 检查。
- `Window_Closed` 清理了大部分控件、集合、定时器和钩子。
- 无 `unsafe`/指针；数组访问有边界检查；P/Invoke 签名与字符串封送基本正确。
- DataGrid 开启行虚拟化与 Recycling，避免大列表一次性创建全部行视觉树。

## 8. 建议修复优先级

### P0（建议优先处理）

1. **执行会话隔离**：为每次执行分配 `sessionId`；工作线程捕获 `sessionId` 和本地 `queue` 引用，循环中同时检查 `sessionId == _execSession && !_execStop`；`Window_Closed`/新执行递增 `_execSession`；`_execWorkers`/计数器按会话隔离或校验会话后再更新。
2. **`_layoutWorkerCount` 生命周期**：在 `ResetRuntimeState`/`Window_Closed` 中复位；使用会话代际或 `Interlocked.Exchange`；`ApplySelectionDiff` 的等待设置上限，超时后记录并继续，而不是永久延迟；`Post` 回调未执行时也要能清理计数。
3. **COM 释放**：在 `GetExplorerSelectedPaths`/`CollectWindowSelection` 中用 `try/finally` 逐个 `ReleaseComObject` 释放 `windowItems`、`Document`、`SelectedItems`、每个选中项；考虑使用 `Marshal.FinalReleaseComObject` 的适用性，避免多引用误释放。
4. **布局与数据串行化**：`ReplaceInputSelection`、`RefreshDates`、扫描启动前等待 `_layoutWorkerCount==0` 或先递增布局代际并等待旧布局退出；不要在工作线程读取 `_files`/行词典时替换/修改它们。更彻底的做法是布局使用不可变快照。

### P1（建议尽快处理）

5. `Window_Closed` 清空 `_data`、`_winContext`、`_lastCaret`、`_execQueue`、`_execDirs`、`_templateHashCheckKey`；关闭 `_presetPopup`；复位 `_scanning`/`_previewDirty`。
6. `TryGetProcessCpuTime` 使用 `using (Process ...)`；`BrowseForRoot` 使用 `using (FolderBrowserDialog ...)`。
7. 为网络/云端IO增加超时/取消；限制扫描/哈希总线程数；关闭窗口时对关键工作线程 `Join` 一个短超时（不要无限等待）。
8. `RunIndexedParallel` 检查 `QueueUserWorkItem` 返回值、给 `done.Wait()` 加超时、超时后回退到内联执行；避免在UI线程执行可能长时间阻塞的并行存在性/哈希检查。
9. 避免嵌套线程池并行：在布局/执行线程池任务中调用BLAKE3时，限制/禁用内层 `Parallel.For`，或使用专用线程/全局信号量。
10. 选择读取线程使用单一长期STA线程+消息泵，或改为 `Task`+超时+可取消的COM调用；至少不要每次重开新线程。

### P2（后续改进）

11. 将跨线程可见的标志改为 `volatile`/`Volatile.Read`。
12. `Window_Closed` 用 `try/finally`；`ResetRuntimeState` 无条件复位所有会话级字段。
13. 为 `_hashCache` 增加容量上限/LRU 或删除行时清理。
14. 明确单实例假设，或把窗口状态改为实例字段/按窗口ID隔离。
15. 增加调试计数器（活动线程数、`_layoutWorkerCount`、`_execWorkers`、RCW计数、进程句柄数），在实机长跑中监控。

## 9. 建议的实机验证

1. 连续打开/关闭窗口100次，开启实时获取，监控进程句柄数、线程数、私有内存；观察是否单调上升。
2. 在扫描/哈希/布局/执行进行中强制关闭窗口或停止Quicker动作，再重新打开，检查：
   - 实时获取是否仍能更新（验证 `_layoutWorkerCount` 是否卡死）；
   - 是否有旧执行线程继续操作文件；
   - 进程句柄/线程数是否回落。
3. 在网络共享/OneDrive占位文件上做选择、扫描、哈希、复制，模拟断网/超时，观察线程是否累积、窗口能否关闭。
4. 快速连续选择100次，用Process Explorer观察RCW/句柄增长；必要时在 `ReleaseComObject` 前后加调试计数。
5. 若Quicker允许，同时打开两个同动作窗口，验证静态状态是否互相干扰。
6. 在调试版挂接 `AppDomain.UnhandledException`/`DispatcherUnhandledException`，记录后台线程和UI线程异常。

## 10. 结论

- **内存安全**：托管代码没有直接内存破坏风险；主要问题是资源生命周期和静态状态泄漏。
- **线程安全**：扫描/哈希/布局的主体设计（分块、代际号、UI发布）是合理的；风险集中在执行线程跨会话、布局与数据修改未串行化、选择读取COM释放和线程池等待。
- **异常退出**：进程被杀死时OS会回收，问题不大；真正需要关注的是 Quicker 长期驻留、窗口异常关闭但进程存活、以及网络IO挂起导致线程/句柄累积。
- 建议先修 P0 的四项，再做 P1 的资源清理和超时/隔离；P2 用于长期稳定性加固。
