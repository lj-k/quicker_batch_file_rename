# 线程安全修复方案评审报告

> 版本：0.01
> 评审对象：`doc/线程安全修复方案.md`（0.01）
> 评审日期：2026-11-18
> 评审团队：架构团队、开发团队、性能团队（并发与测试视角参与）
> 评审结论：有条件通过；P0需补充6项后方可实施

## 0. 结论摘要

方案的方向、分层和P0/P1/P2排序基本正确，但当前P0只覆盖了“会话、快照、计数、COM、哈希缓存”五条主线，仍不足以支撑“P0完成即可作为稳定版”的结论。本次评审新增6项P0缺口、8项P1缺口/修正、2项P2调整，并顺带发现4项功能正确性问题。

| 评审项 | 结论 | 说明 |
|---|---|---|
| 总体方向 | 通过 | 会话隔离、不可变快照、资源所有权、失败复位的主线正确 |
| P0完整性 | 不通过 | 缺少执行快照、关闭超时、单实例前置、布局代际校验、执行期变更门禁、初始化/原生回调保护 |
| P1设计 | 有条件通过 | 并发预算的线程静态标记不可行，`RunIndexedParallel`晚写、发布线程看门狗、COM STA、取消与清理边界需补 |
| P2排序 | 通过 | LRU、分批刷新、缓冲调优可保留在P2 |
| 功能正确性 | 需另立缺陷 | 大小写重命名、再次执行、执行后状态未刷新、长路径/保留名不在线程安全方案内，但应记录 |

**最终意见：** 方案可以有条件通过，但必须把第6.1节的P0-A至P0-F并入P0，并修正P1-A至P1-H后再进入实施。未完成这些修订前，不得宣称“P0完成”或“资源长期稳定”。

## 1. 评审范围与方法

### 1.1 范围

- 修复方案：`doc/线程安全修复方案.md`（0.01）。
- 代码：`src/CustomWindow.Aux.cs`、`src/RenamerCore.cs`、`src/CustomWindow.xaml`。
- 上游文档：`doc/线程安全与内存安全评审报告.md`（0.01）、`doc/需求文档.md`第34章。
- 现有测试与构建：`tests/`、`tools/build_tests.py`、`tools/build_quicker_code.py`、`tools/build_release.py`、`tools/validate_delivery.py`。

### 1.2 方法

1. 逐条把方案措施映射到现有代码位置，确认“措施是否覆盖真实触发路径”。
2. 按“正常、关闭、异常、资源失败、并发变更、宿主多窗口”六类场景反推。
3. 对每条措施检查三个问题：是否有明确所有者、是否有失败复位、是否有可验证的验收。
4. 不进行Windows/Quicker实机运行；运行时结论以现有静态证据和代码路径为准，实机项列入验收。

### 1.3 判定口径

- **通过**：措施能覆盖主要触发路径，验收可执行。
- **有条件通过**：方向正确，但缺少关键环节或存在设计错误，修订后可实施。
- **不通过**：按当前方案实施仍会留下可崩溃、可重复执行、可永久卡死或可长期累积的问题。

## 2. 方案的正确之处

1. **以会话为边界**：把窗口、扫描、哈希、布局、执行、选择读取统一挂到`WindowSession`，方向正确，能从根本上解决静态状态跨窗口污染。
2. **布局改为不可变快照**：`FileSnapshot`+`LayoutRequest`把后台计算与UI行数据解耦，能消除`_files`边读边改的主要数据竞争。
3. **资源所有权显式化**：`ComScope`、定时器清单、Popup关闭、Process/Dialog释放，补上了原代码“获取容易、释放分散”的短板。
4. **哈希缓存引入文件身份**：长度、修改时间、算法和代际校验，能同时解决“旧结果覆盖新结果”和“外部修改后仍用旧哈希”两类问题。
5. **保留`_data`/`_winContext`**：没有把Quicker数据映射写回载体误当普通缓存清空，避免了关闭时输出丢失。
6. **PR拆分合理**：先骨架、再执行、再布局、再计数、再资源、再失败路径、再UI/预算，顺序符合依赖关系。

## 3. P0级缺口

### G-01 执行队列仍持有UI行词典，缺少稳定文件标识与执行快照

**严重度：P0（高）**

**方案现状：** 方案P0-1要求“执行线程使用自己的`ExecutionSession`队列”，但没有定义队列元素的所有权，也没有定义执行结果如何映射回可能已经变化的行列表。

**代码证据：**

- `StartExecution`直接把`_files[i]`加入队列：`src/CustomWindow.Aux.cs:5262-5274`。
- `ExecuteOneFile`在worker线程直接读取`item["Action"]`、`item["SourcePath"]`、`item["TargetPath"]`：`src/CustomWindow.Aux.cs:5376-5378`。
- `ReportExecutionRow`在UI回调中直接修改同一个`item`：`src/CustomWindow.Aux.cs:5617-5636`。
- 配置防抖`ApplyUiConfig`没有检查`_executing`，仍可调用`RefreshDates`/`RecomputeAll`：`src/CustomWindow.Aux.cs:1504-1558`。
- 选择差异定时器也没有检查`_executing`，可在执行期间调用`ApplySelectionDiff`：`src/CustomWindow.Aux.cs:3976-3979`。

**触发场景：**

1. 执行开始后，用户改动某个未禁用控件或此前排队的防抖回调触发重算，行的`Action`/`TargetPath`被改写；worker读到新目标，实际文件操作与用户确认的队列不一致。
2. 执行期间选择差异定时器触发`ApplySelectionDiff`，`_files`被增删；worker仍持有旧词典，结果写回旧对象，界面看不到，旧对象被队列长期引用。
3. `ReplaceInputSelection`或`ApplySelectionDiff`后，按索引映射结果会错行；按词典引用映射则会指向已移除行。

**后果：** 误移动/误复制/误删、结果错行、旧行词典长期滞留、同一次执行出现“界面显示的目标”和“实际写入的目标”不一致。

**必须补充：**

1. 新增`FileId`（`long`或`Guid`），在`BuildFileItem`/`AddFileBatch`时分配，行词典保存`FileId`。
2. 新增不可变`ExecutionItem`，至少捕获：`FileId`、`SourcePath`、`TargetPath`、`Action`、`HashHex`、`IsSkipped`、`Algorithm`、`Digits`、`Prefix`、`Suffix`、`TemplateNeedsHash`、`VerifyEnabled`。
3. `ExecutionSession.Queue`只放`ExecutionItem`，worker不得读取`_files`或行词典。
4. `ReportExecutionRow`改为按`FileId`在当前会话行列表中查找；找不到则记录“行已移除”，不得写旧词典。
5. 执行期间禁止`ReplaceInputSelection`、`ApplySelectionDiff`、`RefreshDates`、`RecomputeAll`；或在执行开始时冻结输入，执行结束后统一刷新。
6. 执行完成后清理`ExecutionSession.Queue`，避免旧行词典被长期引用。

**验收：**

- 执行中触发配置防抖/选择差异100次，实际执行的目标路径始终等于队列快照。
- 执行中移除一半行，结果只更新仍存在的`FileId`，无错行、无空引用。
- 执行完成后`ExecutionSession.Queue`为空，旧行词典可被GC。

### G-02 `Window_Closing`可能永久等待，`ShutdownSession`永远不会执行

**严重度：P0（高）**

**方案现状：** 方案P1-3把清理放在`ShutdownSession`，但没有解决“关闭事件本身被无限期挂起”的问题。

**代码证据：**

- `Window_Closing`在`_executing`为真时设置`e.Cancel=true`，等待执行完成：`src/CustomWindow.Aux.cs:5841-5860`。
- `_executing`只有在`PostExecutionCompleted`中才置为`false`：`src/CustomWindow.Aux.cs:5717-5724`。
- 执行线程启动失败时`_execWorkers`已预置为`parallel`，但未启动的线程不会递减：`src/CustomWindow.Aux.cs:5331`、`5346-5351`。
- 同卷`File.Move`/跨卷`File.Move`没有取消令牌，网络路径或锁冲突可能长时间阻塞：`src/CustomWindow.Aux.cs:5503-5517`。

**触发场景：**

1. 执行线程启动失败，`_executing=true`但无worker，关闭确认后永远等不到完成回调。
2. 某个文件在离线网络路径/被其他进程锁定，`File.Move`阻塞；`_execStop`只在文件之间或复制回调中检查，无法中断该调用。
3. 用户确认关闭后，窗口保持“正在停止执行”状态，既不能关闭也不能操作，`Closed`不触发，`ShutdownSession`不执行。

**后果：** 窗口永久卡死、资源无法释放、用户只能结束Quicker进程，未完成文件操作状态不可控。

**必须补充：**

1. 增加`ClosingState`：`Normal → Stopping → ForceClosing → Closed`。
2. `Window_Closing`设置停止后启动关闭超时（建议5秒）；超时后不再等待执行完成，直接进入`ForceClosing`，允许窗口关闭。
3. 超时后把会话标记为`Detached`，所有后台回调只检查会话、不触碰UI；worker完成后自行退出，允许成为孤儿后台线程。
4. `ShutdownSession`只在`Window_Closed`执行；`ForceClosing`不得跳过它。
5. 线程启动失败必须递减`_execWorkers`并触发一次完成回调，不能让`_executing`永久为真。
6. 界面明确显示“已强制关闭，仍有N个后台操作在收尾”，不得宣称“已全部停止”。

**验收：**

- 注入启动失败、网络挂起、文件锁三类故障，窗口均能在5秒内关闭。
- 强制关闭后重开，旧worker不能修改新窗口、不能关闭新窗口、不能执行新队列。
- 关闭后进程线程数允许短期高于基线，但在操作结束后回落；不要求零残留线程。

### G-03 单实例保护放在P2过晚，P0会话模型默认只有一个活动窗口

**严重度：P0（高）**

**方案现状：** 方案把“单实例保护或实例状态”放在P2；但P0的`WindowSession`、`_session`、静态控件引用和`_data`都按单活动窗口设计。

**代码证据：**

- `_window`、`_data`、`_winContext`是静态字段：`src/CustomWindow.Aux.cs:42-44`。
- `OnWindowCreated`直接覆盖：`src/CustomWindow.Aux.cs:299-301`。
- `OnWindowLoaded`再次覆盖：`src/CustomWindow.Aux.cs:327-329`。
- `Window_Closed`有`ReferenceEquals`守卫：旧窗口迟到时直接return：`src/CustomWindow.Aux.cs:6051-6053`；随后才统一置空静态控件引用：`src/CustomWindow.Aux.cs:6094-6163`。

**触发场景：**

1. 用户从Quicker同时打开两个窗口，第二个覆盖`_window/_data`，第一个的后台回调操作第二个的控件或数据。
2. 旧窗口`Closed`晚于新窗口`OnWindowCreated`执行，守卫使旧窗口直接return；新窗口的全局引用没有被旧窗口置空，但旧窗口自己的`_session`、`_rows`、`_files`、`_execQueue`、COM对象和定时器也没有被清理。
3. 旧窗口`PostExecutionCompleted`把全局`_closeAfterExecution`解释为自己的状态，关闭新窗口：`src/CustomWindow.Aux.cs:5728-5733`。

**后果：** 跨窗口状态污染、旧窗口资源泄漏、误关闭新窗口、数据映射写到错误窗口、会话校验失效。守卫避免了“旧窗口清空新窗口引用”，但没有解决“旧窗口自己的会话没人清理”。

**必须补充（二选一）：**

- **推荐P0方案：单活动窗口守卫。** `OnWindowCreated`发现已有未关闭会话时，激活旧窗口并拒绝新窗口初始化；`OnWindowLoaded`检测拒绝标记后直接返回。`Window_Closed`只在`ReferenceEquals(_session, closedSession)`时清空全局引用。
- **彻底方案：实例化状态。** 把所有可变静态字段移入`WindowSession`，静态只保留`_currentSession`；工作量大，不建议在P0做。

**验收：**

- 同时打开两个窗口，第二个被拒绝或激活第一个，不出现两个活动会话。
- 旧窗口延迟关闭，不影响新窗口的`_window`、`_data`、`_config`、`_session`。
- 旧执行完成后不得关闭新窗口。

### G-04 `ApplyLayouts`只校验DataVersion不够，必须校验布局代际

**严重度：P0（高）**

**方案现状：** 方案P0-2写的是“校验会话、快照版本、长度”，没有明确校验`LayoutRequest`对应的`RecomputeGeneration`。

**代码证据：**

- 配置变化会递增`_recomputeGeneration`，但未必改变`DataVersion`。
- 旧布局结果在配置变化后仍可能通过“会话相同、DataVersion相同、长度相同”的校验。
- `ApplyLayouts`当前按`_files.Count`循环写行：`src/CustomWindow.Aux.cs:2829-2862`。

**后果：** 用户改了模板/算法/日期源后，旧布局结果覆盖新配置，界面显示旧目标；若旧布局基于旧快照，还可能把错误目标写进执行队列。

**必须补充：**

1. `LayoutRequest`增加`Generation`，由`session.RecomputeGeneration`在发起时捕获。
2. `ApplyLayouts`必须同时满足：`ReferenceEquals(request.Session, _session)`、`request.Session.Closed == false`、`request.Generation == Volatile.Read(ref session.RecomputeGeneration)`、`request.DataVersion == session.DataVersion`、`request.Snapshot.Length == layouts.Length`、当前行数不小于快照长度。
3. `FinalizeLayouts`的代际检查统一改为`request.Generation`，不要继续读全局`_recomputeGeneration`。
4. 任一项不满足，丢弃结果并记录丢弃原因；不得部分应用。

**验收：**

- 连续快速改模板10次，只有最后一次结果被应用。
- 旧布局晚到时不改变任何行、不改变执行队列。
- 布局结果长度与快照不一致时不越界、不部分写入。

### G-05 执行期间缺少统一变更门禁

**严重度：P0（高）**

**方案现状：** 方案有“UI线程异步化”和“执行会话”，但没有规定执行期间哪些UI/后台入口必须停止修改行数据。

**代码证据：**

- `ApplyUiConfig`只检查`_suppressEvents`/`_config`，不检查`_executing`：`src/CustomWindow.Aux.cs:1484-1558`。
- `EnsureHashWorker`不检查`_executing`：`src/CustomWindow.Aux.cs:2181-2227`。
- `ApplySelectionDiff`不检查`_executing`：`src/CustomWindow.Aux.cs:3844-3852`。
- `HandleSelectionReadResult`的手动路径不检查`_executing`：`src/CustomWindow.Aux.cs:3520-3530`。
- `_selectionApplyTimer`只检查实时获取开关，不检查执行状态：`src/CustomWindow.Aux.cs:3966-3980`。
- `RefreshSelection_Click`有检查，但先前排队的读请求仍可能在执行开始后返回并调用`ReplaceInputSelection`。

**后果：** 执行worker读取的`Action`/`TargetPath`被改写；`_files`被替换；哈希/布局与执行争抢磁盘；结果错行或误操作。

**必须补充：**

1. `WindowSession`增加`Executing`状态，所有修改`_files`、行布局字段、配置派生结果的入口统一检查。
2. 执行开始时：停止防抖定时器、取消待处理选择差异、暂停哈希、禁止布局重算；执行结束后统一恢复一次重算。
3. `HandleSelectionReadResult`在手动和实时两条路径都检查`Executing`；手动请求返回时若已执行，丢弃并提示。
4. `ApplySelectionDiff`入口和定时器回调都检查`Executing`；已排队的差异直接清空，不延迟到执行中。
5. 即使G-01已改为执行快照，仍要在执行期间禁止替换`_files`，避免输出和界面状态混乱。

**验收：**

- 执行中改配置、切换实时获取、重新获取选择，实际执行目标不变。
- 执行中不出现哈希/布局/选择差异同时改行。
- 执行结束后自动恢复一次正确重算。

### G-06 初始化和WinEvent原生回调缺少顶层异常保护

**严重度：P0（高）**

**方案现状：** 方案有“失败路径/关闭”PR，但没有把`OnWindowLoaded`初始化失败和WinEvent回调异常列为P0。

**代码证据：**

- `OnWindowLoaded`先设置静态引用，再`PrimePresetVariables`、`FindControls`、`ResetRuntimeState`、`AttachEvents`、`StartScan`，全程无try/catch：`src/CustomWindow.Aux.cs:324-355`。
- `SelectionEventCallback`是`SetWinEventHook`的原生回调，函数体无try/catch：`src/CustomWindow.Aux.cs:4059-4069`。
- `ScheduleRealTimeSelectionRefresh`已有try/catch并在投递失败时重置`_selectionEventQueued`：`src/CustomWindow.Aux.cs:4080-4137`；该点无需重复修复，但原生回调本身仍需顶层保护。
- `ScheduleRealTimeSelectionRefresh`在进入前读取`_window`，随后使用`_window.Dispatcher`；若窗口在这两步之间关闭，虽然有try/catch兜底，仍应捕获局部引用，减少异常路径。

**后果：**

- XAML控件名不匹配、预设变量读取异常、扫描线程启动异常时，窗口处于半初始化状态，后续`Closed`也未必能清干净。
- WinEvent回调异常跨越原生边界，可能直接终止Quicker进程。

**必须补充：**

1. `OnWindowLoaded`整体try/catch；失败时调用`ShutdownSession`，显示可读错误，不启动任何线程。
2. `SelectionEventCallback`整体try/catch/finally，任何异常不得逃逸到原生边界。
3. 保留`ScheduleRealTimeSelectionRefresh`现有的try/catch与`_selectionEventQueued`复位；改为先捕获局部`Window window`，再使用`window.Dispatcher`。
4. `Post`统一在内部执行`action`时try/catch，记录异常，避免单个UI回调异常终止宿主。
5. 初始化顺序调整为：先`FindControls`校验全部控件，再`ResetRuntimeState`，最后启动扫描/哈希。

**验收：**

- 注入控件缺失、预设读取异常、线程启动异常，窗口可关闭且无残留定时器。
- 关闭窗口瞬间触发WinEvent，不崩溃、不永久禁用实时获取。
- `Post`回调抛异常时只记录，不影响后续回调。

## 4. P1级缺口与设计修正

### G-07 并发预算的`[ThreadStatic]`标记不能阻止`Parallel.For`嵌套

**严重度：P1（高）**

**方案现状：** 方案5.5计划“父任务在调用哈希前设置`[ThreadStatic] _insideParallelWorker=true`，子任务检查后不再申请预算”。

**问题：** `[ThreadStatic]`只对当前线程有效；`Parallel.For`会把工作项分派到其他线程池线程，这些线程的标记为`false`，仍会申请预算或继续嵌套并行。若预算用`SemaphoreSlim.Wait()`，父任务持有租约等待子任务、子任务等待租约，可能死锁。

**必须修正：**

1. 给`ComputeHashHex`/`ComputeBlake3Hex`增加`allowParallel`或`maxParallelism`参数。
2. 布局比较、执行后校验等已经在并行worker内的调用，显式传`allowParallel=false`，让BLAKE3串行处理该文件。
3. 只有独立哈希worker可以使用BLAKE3内部分块并行。
4. 预算层使用可重入租约或“已持有则跳过申请”；UI线程不得同步`Wait()`预算。
5. 预算上限按“CPU型”和“IO型”分开，不要用一个信号量同时限制两者。

**验收：**

- 8个比较worker同时比较大文件，不出现线程池饥饿或死锁。
- BLAKE3内部并行数不超过配置，且不与比较worker叠加超过CPU上限。
- UI线程执行操作时不同步等待预算。

### G-08 `RunIndexedParallel`超时后仍可能晚写结果和释放竞争

**严重度：P1（高）**

**方案现状：** 方案要求“超时返回、晚`Signal`处理、body异常汇总”，但没有规定晚到工作项如何避免写共享结果。

**代码证据：**

- `RunIndexedParallel`在`done.Wait()`返回后继续使用/释放计数对象：`src/CustomWindow.Aux.cs:2907-2954`。
- `FinalizeLayouts`只在任务开始时检查代际，随后直接写`layouts[index]`：`src/CustomWindow.Aux.cs:2670-2695`、`2711-2733`。

**必须修正：**

1. 每个工作项把结果写入线程本地/索引槽位的临时对象，提交时在锁或会话门禁下检查代际，再合并。
2. 超时后不立即`Dispose` `CountdownEvent`；用独立的“已排队/已完成”计数，确认所有排队项结束后再释放，或接受不释放并让GC回收。
3. `Signal`包在try/catch中，捕获`ObjectDisposedException`。
4. 超时后设置`Abandoned`，晚到结果直接丢弃，不写`layouts`。
5. `body`异常必须汇总到调用方，不能只记录后继续。

**验收：**

- 注入慢任务/晚到任务，超时后无晚写、无`ObjectDisposedException`。
- 结果数组在超时后保持不变。
- 调用方能收到异常摘要。

### G-09 扫描发布线程可能永久等待缺失分块

**严重度：P1（高）**

**方案现状：** 方案有“线程启动失败”和“工作项超时”，但没有覆盖扫描发布线程的“分块永远不就绪”。

**代码证据：**

- 发布循环的结束条件是`workersRemaining == 0 && published >= chunkCount`：`src/CustomWindow.Aux.cs:1855`。
- 如果某个worker在写入`chunkReady[published]`前异常退出，`workersRemaining`会归零，但`published < chunkCount`，循环永远不满足结束条件，只每50ms`Monitor.Wait`：`src/CustomWindow.Aux.cs:1856-1857`。
- 线程启动失败时`workersRemaining`保持初始值，也会卡住。

**必须修正：**

1. 发布线程发现`workersRemaining == 0 && published < chunkCount`时，判定扫描不完整：记录缺失分块，补齐空结果或标记失败，退出循环。
2. 增加扫描看门狗（如30秒无进展），超时后取消本次扫描并提示。
3. `Thread.Start`失败按实际启动数初始化`workersRemaining`，或在失败时递减。
4. `FinishScan`只在所有分块发布完成时调用；不完整时显示“部分文件读取失败”，不得静默。

**验收：**

- 注入worker在写入分块前退出，发布线程在有限时间内退出。
- 启动失败不产生永久“正在读取文件属性”。
- 部分失败的文件数与提示一致。

### G-10 COM释放必须在获取它的STA线程执行，并容忍重复/无效对象

**严重度：P1（高）**

**方案现状：** 方案P0-4要求`ComScope`逆序释放，但没有规定释放线程和异常策略。

**代码证据：**

- `CollectWindowSelection`在STA选择读取线程获取`Document`、`SelectedItems`、选中项：`src/CustomWindow.Aux.cs:3618-3644`。
- `GetExplorerSelectedPaths`在UI线程获取`Shell.Application`、`Windows`、`windowItems`：`src/CustomWindow.Aux.cs:3565-3616`。
- 现有`ReleaseComObject`只做null检查：`src/CustomWindow.Aux.cs:3721-3731`。

**必须修正：**

1. `ComScope`由获取对象的线程创建和释放；不得在`ShutdownSession`的UI线程释放选择读取线程的COM对象。
2. 每个`ReleaseComObject`独立try/catch；无效/已释放对象记录后继续，不中断后续释放。
3. 释放顺序：选中项/枚举器 → `SelectedItems` → `Document` → windows集合 → `Shell.Application`。
4. 对同一RCW重复登记做去重或引用计数，避免过度释放。
5. 释放后把字段置空，防止二次使用。

**验收：**

- 快速选择1000次，RCW/句柄不单调增长。
- 注入空Document、非Explorer窗口、已释放对象，不抛异常到UI。
- 关闭窗口不跨公寓释放COM对象。

### G-11 哈希/比较缺少取消和完整的一致性校验

**严重度：P1（高）**

**方案现状：** 方案P0-5增加了哈希缓存的长度/修改时间校验和`FileShare.Delete`，P1-6提到“读取共享模式与一致性”，但没有把取消令牌和比较路径纳入。

**代码证据：**

- `ComputeHashHex`以`FileShare.ReadWrite`打开文件，读取过程无取消检查：`src/RenamerCore.cs:1401`。
- `ComputeBlake3Hex`的`Parallel.For`没有`CancellationToken`或`Func<bool>`：`src/RenamerCore.cs:1807-1843`。
- `TryCompareFileContent`同样以`FileShare.ReadWrite`打开源和目标，无`FileShare.Delete`：`src/RenamerCore.cs:599-601`。
- 云端占位文件可能触发水合下载，当前没有超时。

**必须修正：**

1. `ComputeHashHex`/`ComputeBlake3Hex`/`ComputeHashHexFromStream`增加`Func<bool> cancel`或`CancellationToken`，每读一块检查一次。
2. `TryCompareFileContent`增加取消参数，并改用`FileShare.ReadWrite | FileShare.Delete`。
3. 哈希和比较都在打开后记录长度/修改时间，结束后再校验一次；不一致则返回“文件已变化”，不写缓存。
4. 对云端占位增加显式检测/提示；默认不自动水合大文件，或给出超时。
5. 哈希缓存只缓存“身份校验通过”的结果；错误哨兵不长期缓存，允许下次重试。

**验收：**

- 关闭窗口/取消执行后，大文件哈希在可接受时间内停止。
- 哈希中外部修改文件，结果标记为无效而不是写入旧值。
- 比较期间执行移动不被`FileShare`阻止。

### G-12 `ShutdownSession`在UI线程同步Join会阻塞，且无法保证线程销毁

**严重度：P1（中高）**

**方案现状：** 方案5.3要求“线程等待使用短超时（如2秒），超时记录并继续清理”，但没有区分哪些线程可以Join、哪些线程可能正在等待UI。

**问题：**

- `SelectionReaderLoop`通过`_window.Dispatcher.BeginInvoke`投递结果；UI线程若Join它，虽然`BeginInvoke`不阻塞，但COM调用可能长时间不返回。
- 执行worker可能阻塞在`File.Move`；`Join`超时后线程仍在运行，方案不能承诺“线程已销毁”。
- 在UI线程同步Join任何后台线程都会造成界面冻结，2秒也不可接受。

**必须修正：**

1. `ShutdownSession`在UI线程只做“标记会话关闭、停止定时器、关闭Popup、解绑事件”，不Join执行/选择线程。
2. 需要Join的线程改为后台自清理：worker检测会话关闭后自行退出，最后递减计数；关闭流程只等待一个短超时的“资源释放完成”事件，不等待线程对象。
3. 明确写入方案：**不承诺强制销毁线程**；不承诺零遗留线程；承诺的是旧线程不能再触碰新会话、不能造成数据损坏。
4. 对无法取消的IO，记录“孤儿操作”计数和最后路径，供用户诊断。
5. 实机验收看“操作结束后线程回落”，不看“关闭瞬间线程为0”。

**验收：**

- 关闭窗口时UI不冻结超过500ms。
- 强制关闭后旧线程完成时不影响新窗口。
- 资源长跑中线程数在操作结束后回落，允许短时高于基线。

### G-13 哈希缓存全表扫描是O(n)，执行/布局高频调用时放大延迟

**严重度：P1（中）**

**方案现状：** 方案把LRU放在P2，但没有处理`EnsureHashWorker`每次都遍历全部`_files`的问题。

**代码证据：**

- `EnsureHashWorker`在`_hashLock`内遍历`_files`构造缺失列表：`src/CustomWindow.Aux.cs:2205-2216`。
- `RecomputeAll`/`ApplyLayouts`/`ApplySelectionDiff`都会触发`EnsureHashWorker`：`src/CustomWindow.Aux.cs:2869`、`3941`、`4009`。

**后果：** 10万行时每次触发布局都可能产生一次全表扫描；如果布局分批应用，扫描次数会成倍增加，抵消之前的性能优化。

**必须修正：**

1. 会话维护`PendingHashPaths`或增量索引，新增行时加入，哈希完成/失效时移除。
2. `EnsureHashWorker`只处理待办集合，不全表扫描。
3. 对同一批布局只触发一次哈希调度，不要在每批`ApplyLayouts`都调用。
4. LRU仍可留在P2，但增量待办集合应在P1完成。

**验收：**

- 10万行、100次布局应用，哈希调度扫描次数不随布局批次线性增长。
- 新增/删除行时待办集合正确更新。

### G-14 关闭清理清单仍需明确“保留/清空/解绑”三类对象

**严重度：P1（中）**

**方案现状：** 方案5.3给出了清理顺序，但`Rows`/`Files`、`_data`、`_winContext`、`_lastCaret`、`_execQueue`、`_presetPopup`的所有权边界仍不够明确。

**代码证据：**

- `Window_Closed`重置`_rows/_files/_paths`，但不清`_execQueue/_execDirs/_lastCaret`：`src/CustomWindow.Aux.cs:6156-6163`。
- `_presetPopup`只置空，不关闭：`src/CustomWindow.Aux.cs:6146`。
- `_execQueue`持有行词典，可能很大。
- `_lastCaret`是`TextPointer`，会持有FlowDocument内部引用。

**必须修正：**

1. 清理清单增加三列：保留（`_data`输出键、`_winContext`）、清空（会话Rows/Files/Paths/HashCache/ExecQueue/ExecDirs/PendingSelectionDiff）、解绑（DataGrid ItemsSource、事件、Popup）。
2. 先解绑`ItemsSource`，再清空集合，避免关闭中的UI刷新。
3. `_lastCaret`在`Window_Closed`置空；新窗口`ResetRuntimeState`已置空，但旧窗口单独关闭时也应释放。
4. `_presetPopup.IsOpen=false`后再置空。
5. `_execQueue`清空后再置空，避免旧行词典滞留。

**验收：**

- 单独打开再关闭窗口（不重开），私有内存和句柄回落。
- 关闭时Popup不可见，DataGrid不再持有旧集合。
- `_data`输出列表仍可供Quicker写回。

## 5. P2级调整与功能正确性问题

### G-15 `_hashCache` LRU保留在P2可以，但需设置硬上限

**严重度：P2（中）**

方案P2已有“10万项上限与LRU”，本次确认保留。补充：上限应按“路径字符串总长度”或“条目数+估算内存”双重限制，避免超长路径导致内存超预期；清理时不得清理当前会话待办中的键。

### G-16 `ApplyLayouts`分批刷新保留在P2可以，但需保证批次间会话一致

**严重度：P2（中）**

分批应用时每批都要检查会话和代际；不能在第一批应用后用户改配置，后续批次仍继续写旧结果。建议每批开始前检查一次，批次大小按行数/耗时自适应。

### F-01 仅大小写不同的重命名被当作“无需操作”

**严重度：功能缺陷（中）**

**代码证据：** `ExecuteOneFile`在`string.Equals(source, target, OrdinalIgnoreCase)`时直接返回“无需操作”：`src/CustomWindow.Aux.cs:5421-5429`。

**后果：** `a.txt → A.txt`不会真正改名，用户以为已重命名。

**建议：** 区分“完全相同”和“仅大小写不同”；仅大小写不同时使用临时文件名两步`File.Move`，或调用系统大小写重命名API。该问题与线程安全无关，建议单独立缺陷，不混入P0。

### F-02 “再次执行”使用旧源路径，移动/重命名后必然失败或重复复制

**严重度：功能缺陷（中）**

**代码证据：**

- 执行完成后按钮改为“再次执行”：`src/CustomWindow.Aux.cs:5741`。
- 执行成功只更新`ExecState/Status`，不更新`SourcePath`，也不重新扫描：`src/CustomWindow.Aux.cs:5619-5636`。

**后果：**

- 移动/重命名后源文件已不存在，再次执行全部报“源文件不存在”。
- 复制后目标已存在，再次执行全部报“目标文件已存在”。

**建议：** 执行完成后禁用“再次执行”，改为“重新获取选择/重新扫描”；或在移动/重命名成功后更新行的源路径并清空旧哈希。需产品确认语义，建议单独立缺陷。

### F-03 执行完成后输入状态未刷新

**严重度：功能缺陷（中）**

**代码证据：** 执行成功只更新`ExecState/Status`，不更新行的`SourcePath`、`HashHex`，也不重新检查源/目标存在性：`src/CustomWindow.Aux.cs:5619-5636`、`5741`。

**后果：** 移动/重命名后界面仍显示旧源路径；目标路径列仍按旧存在性显示；哈希缓存仍以旧源路径为键；筛选/排序结果与磁盘不一致，并直接导致“再次执行”失败。

**建议：** 执行完成后按动作类型更新行模型（移动/重命名更新源路径，复制保持源路径），清空受影响行的哈希缓存，重新检查目标存在性；或提示用户“重新获取选择”。该问题与F-02同源，建议合并为一个“执行后状态刷新”缺陷。

### F-04 长路径与Windows保留名未在方案中覆盖

**严重度：功能缺陷（低）**

**问题：** .NET Framework 4.8默认受MAX_PATH限制；`CON`、`PRN`、`AUX`、`NUL`、`COM1`等保留名、结尾空格/点、非法字符可能导致创建/移动失败。方案没有在目标路径生成阶段统一校验。

**建议：** 在`TryBuildTargetPath`或布局后增加目标路径合法性校验，明确提示；长路径按Quicker宿主是否启用longPathAware决定，未确认前不要承诺支持。该问题与线程安全无关，列入功能缺陷池。

## 7. 性能团队评审

### 7.1 并发预算建议值

按代码路径估算，扫描最多12、哈希1、布局8、比较8、执行1~8、BLAKE3内部最多8、选择读取1。若不限制，理论上可同时出现数十个CPU/IO线程。

| 类型 | 建议上限 | 说明 |
|---|---|---|
| CPU型（哈希/比较/BLAKE3） | `max(1, ProcessorCount / 2)`，且不超过8 | 避免与UI/扫描争抢 |
| IO型（扫描/复制/移动） | 12 | 网络路径按主机再限流 |
| 布局 | 8 | 保留现有上限 |
| 执行 | 1~8，按用户配置 | 不与BLAKE3内部并行叠加 |
| 总线程目标 | 不超过`ProcessorCount * 2 + 4` | 超出时排队而非新建 |

### 7.2 性能验收基线

| 场景 | 基线 | 验收 |
|---|---|---|
| 0.06.21扫描 | 现有实机数据 | 不低于基线90% |
| BLAKE3 64MB | 三次中位数约196 MB/s（Mono本地） | 不低于基线90% |
| 1000行布局 | 现有实机数据 | 不低于基线90%，UI无>500ms冻结 |
| 10万行哈希调度 | 当前O(n)全表扫描 | P1后调度扫描次数不随布局批次线性增长 |
| 执行+哈希+选择30分钟 | 无基线 | 无卡死、无队列堆积、内存不单调上升 |

### 7.3 性能风险排序

1. **P0执行快照**会新增每项复制，但相对文件IO可忽略；不得因优化复制而继续共享行词典。
2. **P1并发预算**可能降低单文件哈希峰值；验收看整体吞吐和UI响应，不看单指标峰值。
3. **P1哈希待办集合**是10万行场景的关键，优先于LRU。
4. **P2 BLAKE3缓冲调优**必须在P1预算稳定后做，否则调优结果不可复现。

### 8.2 Windows/Quicker实机

1. 连续开关100次；记录私有内存、句柄、线程，关闭后允许短期高于基线，操作结束后回落。
2. 执行中关闭再打开；旧worker不得影响新窗口。
3. 布局中反复重新获取；观察是否崩溃/错行。
4. 快速选择1000次；观察COM/句柄。
5. 哈希中外部修改/替换文件；校验码必须变化或标记失效。
6. 网络断开/OneDrive占位；不得永久卡死。
7. 同时打开两个窗口；第二个被拒绝或激活第一个。
8. 强制结束Quicker；确认无持久化损坏（临时文件/半复制文件需在下次执行时能识别）。
