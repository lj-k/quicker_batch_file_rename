### 2.8 日期递补与解析

- 主选存在 → 主选优先。
- 主选缺失、递补1可用 → 按顺序取下一个可用日期。
- 递补选择【空值】→ 返回空日期并停止，三个日期胶囊都为空。
- 递补选择【自定义】→ 返回统一自定义值并停止，三个日期胶囊都替换。
- 递补选择【跳过】→ 标记该文件跳过，不处理、不输出。
- 递补顺序重复项去重并按5槽补齐；`跳过,自定义,空值,文件名,创建` 等中文别名可识别。
- 默认顺序 `filename,exif,modified,created,empty`。
- 旧版 `dateFallback5Text`、旧四槽顺序可迁移。

### 2.11 过滤器与动作匹配

- 扩展名规范化：`*.JPG, .png | mp4 jpg` → `jpg;png;mp4`（大小写统一、去点、去重）。
- `skip` 模式：命中列表跳过，未命中保留。
- `copy/move/rename` 模式：未命中跳过，命中保留。
- 空列表不执行过滤。
- `*` 通配全部：`skip` 模式全部跳过，`rename` 模式全部保留。
- 中文别名：跳过/复制/移动/重命名分别规范化为 skip/copy/move/rename。
- 动作匹配：
  - `rename` + 同目录 → 重命名。
  - `rename` + 目标目录变化 → 复制。
  - `copy` → 复制；`move` → 移动。
  - 白名单模式未命中 → 跳过；跳过模式命中 → 跳过。
  - 跳过模式未命中 + 同目录 → 重命名；目标目录变化 → 复制。

## 5. 风险与限制

| 风险 | 影响 | 缓解 |
|---|---|---|
| Quicker 实机 WPF/C# 5 环境差异 | XAML 控件或 `System.Windows.Forms` 引用可能需调整 | 已按官方文档与 C# 5 编写；提供实机测试清单 |
| DataGrid 绑定到词典索引器 | 行刷新/ToolTip 显示可能因 Quicker 修改版 WPF 而异 | 使用 `Items.Refresh()`；实机优先验证 |
| 静态状态与多窗口 | 同时打开多个窗口可能互相覆盖状态 | 按单实例使用；关闭事件校验窗口引用 |
| EXIF 依赖系统编解码器 | 部分 HEIC/WebP/RAW 读不到日期 | 回退到修改/创建日期；提示来源 |
| 哈希耗时 | 大文件/BLAKE3 计算较慢 | 后台线程、进度、缓存、按需计算 |
| 跨平台长度限制 | 部分系统可接受的长路径被提前拒绝 | 阈值可调整；错误提示明确 |
| 实时刷新关闭 | 用户可能忘记点击预览 | 状态提示、生成输出禁用、预览按钮启用 |
| 旧嵌套结构遗留 | 旧版 `{presetVersion, presets}` 状态仍在变量中 | 读取时自动识别并迁移；保存时统一写扁平结构 |
| 执行文件操作 | 复制/移动/重命名不可完全回滚，磁盘/权限/占用可能导致部分失败 | 逐项报错并继续；目标不覆盖；跨卷移动先复制校验后删除 |
| 执行后校验耗时 | 大文件/BLAKE3需重读目标文件，总耗时增加 | 可关闭执行后校验；进度与速度可见 |
| 执行中关闭窗口 | 长文件操作可能延迟关闭 | 确认后停止领取新任务，等待已开始项目完成 |
| 原生复制兼容性 | 极少数虚拟文件系统/加密文件不支持 `CopyFileEx` | 仅对不支持类错误回退托管流；其他错误报错并重试 |
| 网络/USB吞吐 | SMB、VPN、USB供电/主控差异导致速度波动 | 按类型选缓冲、网络重试、可移动盘落盘刷新；需实机调优 |
| SSD/HDD介质区分 | 标准 `DriveInfo` 无介质类型，无法自动区分 | 固定盘统一策略，大文件4 MiB；必要时引入WMI（Q-14） |
| 进程崩溃残留临时文件 | 复制中进程崩溃可能留下 `.qk-*.tmp` | 临时文件不带目标文件名，不影响目标；后续可增加启动清理 |
| 同卷移动校验语义 | 同卷移动不再重算内容哈希，若磁盘层发生静默损坏不会被发现 | 同卷移动只改名、不写内容；关键场景可改用复制+校验；跨卷移动仍内容校验 |
| EXIF 元数据模式兼容性 | 极少数编解码器在 `BitmapCacheOption.None` 下元数据读取失败 | 失败时回退为无EXIF日期，再按递补顺序取值；实机验证HEIC/WebP |

| 本地元数据扫描模型：4线程 | 513,553 文件/秒 | 约2.57倍，当前3 vCPU最佳 |
| 本地元数据扫描模型：8线程 | 487,986 文件/秒 | 开始回落 |
| 本地元数据扫描模型：12线程 | 450,983 文件/秒 | 继续回落 |

性能判断：

- 目标路径、日期提取、JSON解析均为CPU型；路径生成单线程约12万/秒，布局并行可进一步降低墙钟时间。
- 哈希为CPU型；CRC32最快，BLAKE3约为CRC32的1/4。大文件建议优先CRC32/MD5，确需强校验再选SHA-256/BLAKE3。
- 冲突比较是I/O+CPU混合：相同文件需要“CRC+逐字节”两轮读取。按本次16 MiB约200ms估算，1 GiB相同文件对约12.8s（估算值，受磁盘/缓存影响），仅发生在目标已存在的冲突行。
- 本地元数据扫描在4线程达到峰值，继续增加线程无收益；OneDrive属网络延迟型，实际最佳线程数需在Windows实机测量，当前扫描上限12、默认按CPU×2且至少4线程，处于合理区间。
- 云占位目标不读取内容，冲突比较不会触发OneDrive下载。
