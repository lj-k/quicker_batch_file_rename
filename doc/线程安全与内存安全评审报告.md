# 线程安全与内存安全评审报告

> 版本：0.01
> 评审日期：2026-11-18
> 复核对象：`doc/线程安全与内存安全分析.md`（0.01）
> 评审团队：架构组、开发组、性能组（含测试与运维视角）
> 评审方式：静态代码审查、跨文件调用链复核、失败场景推演
> 评审结论：**有条件通过（Conditional Pass）**

## 0. 结论摘要

1. 原分析报告的总体判断成立：项目没有`unsafe`、指针、`stackalloc`、`fixed`或手工非托管内存分配，不存在传统缓冲区溢出、悬垂指针或直接内存破坏。
2. 原报告的4项高风险全部确认，且均有范围扩大或具体化：
   - 执行线程跨会话问题确认，并发现`PostExecutionCompleted`会把`_execStop`重置为`false`，旧线程可能因此继续运行。
   - `_layoutWorkerCount`问题确认，并补充Dispatcher关闭后回调被丢弃、计数永久不归零的路径。
   - COM释放问题确认，并扩大到`Document`、`SelectedItems`、选中项、`windowItems`集合和COM枚举器。
   - 布局线程与`_files`/行词典并发问题确认，并给出可触发的`ApplyLayouts`越界崩溃路径。
3. 原报告有1处结论需要修正：`DebounceTimer_Tick`直接空引用`_config`的判断不成立，因为`ApplyUiConfig`已有`_config == null`保护；真实风险应改为“其他关闭后回调与`_window`检查后使用”。
4. 本轮“举一反三”新增/细化33条问题，其中P0级5项、P1级13项、P2级15项（含对原结论的扩大与具体化）。最需要优先处理的是：
   - 缺少统一的窗口会话/生命周期令牌，异步任务只靠零散代际号判断。
   - `ReplaceInputSelection`不递增重算代际、不等待布局线程，存在`ApplyLayouts`数组越界崩溃路径。
   - 哈希缓存存在“旧代际晚写覆盖新结果”和“重新获取文件后继续使用旧哈希”的正确性问题。
   - 扫描/哈希/执行线程`Thread.Start()`失败时计数器不复位，可能永久卡死或发布线程死循环。
   - 嵌套并行没有全局预算，布局比较、哈希线程、执行校验可能同时抢占线程池。
5. 建议按P0→P1→P2分三阶段整改；P0未完成前，不建议把当前版本作为长期驻留Quicker进程的稳定版交付。

### 1.2 方法

1. 逐项复核原报告结论，定位到具体字段、方法、线程和回调。
2. 沿着“谁创建、谁持有、谁释放、谁在什么线程访问”四条链路检查资源生命周期。
3. 对每个异步入口检查：是否有会话标识、是否有代际校验、失败路径是否复位、回调是否可能在窗口关闭后执行。
4. 对每个共享集合检查：是否只在UI线程修改、后台是否读取同一可变对象、是否使用快照。
5. 对每个并行入口检查：是否可能嵌套、是否有全局并发预算、是否可能阻塞线程池。

### 1.3 限制

- 当前环境为Linux，无法运行Windows/Quicker/WPF实机，无法测量真实句柄、线程、RCW和私有内存曲线。
- COM引用计数、WinEvent投递线程、Quicker宿主异常策略属于运行时行为，本报告给出静态推演和验收方法，最终以Windows实机长跑为准。
- 本报告只做评审，不修改代码。整改实施后需重新执行测试、构建和交付校验。

### 3.4 复核修正

#### 修正1：`DebounceTimer_Tick`空引用`_config`的结论不成立

原报告认为关闭后已排队的`DebounceTimer_Tick`可能因`_config`为空而抛空引用。复核结果：

- `DebounceTimer_Tick`（`:1477-1482`）本身确实没有`_window`或`_config`检查。
- 但它调用的`ApplyUiConfig`在`:1484-1487`第一行就有`if (_suppressEvents || _config == null) return;`。
- `Window_Closed`在最后才把`_config`置空（`:6163`），而UI线程是串行的，已排队的Tick要么在置空之前执行，要么在置空之后被上述保护拦截。

因此该条应从“中风险空引用”降为“低风险待审计”，真实风险改为：其他关闭后回调是否都有同等保护，以及`_window`“先检查后使用”是否可能被关闭打断。该项已在新增问题D-09中重新表述。

#### 修正2：BLAKE3嵌套并行的外层不是线程池

原报告写“BLAKE3`Parallel.For`嵌套在线程池任务中”。更准确的链路是：

```text
布局专用后台线程
  └─ FinalizeLayouts
       └─ RunIndexedParallel（线程池工作项）
            └─ TryCompareFileContent
                 └─ ComputeHashHex
                      └─ BLAKE3 Parallel.For（再次使用线程池）
```

外层布局线程不是线程池线程，但中间的`RunIndexedParallel`工作项是线程池线程，且它在等待内层`Parallel.For`。这仍然会造成线程池阻塞和线程注入延迟，只是不是“最外层就是线程池”那么简单。

#### 修正3：`CountdownEvent`释放竞争当前不会发生

`RunIndexedParallel`当前是无限`done.Wait()`，只有全部`Signal`后才会离开`using`，因此不存在“晚Signal撞上Dispose”。一旦按建议增加超时，才会出现该竞争，必须在`Signal`处加`try/catch (ObjectDisposedException)`，或在超时后仍等待所有工作项退出。

#### 修正4：COM释放要区分“借用引用”和“自有引用”

原报告的方向正确，但实施时不能机械地对每个`object`都调用`Marshal.ReleaseComObject`：

- 从COM集合枚举出来的元素，封送器通常会为托管侧增加引用，逐个释放是合理的。
- 同一个RCW可能被多次返回；如果重复释放同一个RCW，可能过度释放。
- 建议建立“获取即登记、释放即注销”的局部所有权表，或在单个方法内用`try/finally`按获取逆序释放，不跨方法传递未登记RCW。

### 4.2 关键新问题详解

#### D-01 `ReplaceInputSelection`与布局线程的越界崩溃路径（P0）

证据：

- `ReplaceInputSelection`（`:3734-3797`）直接替换`_files`，没有递增`_recomputeGeneration`，也没有等待`_layoutWorkerCount`归零。
- `ApplyLayouts`（`:2829-2862`）以“当前`_files.Count`”为循环上界，却索引布局线程早先按旧数量生成的`layouts`数组。

可触发时序：

1. 输入列表有1000行，布局线程开始计算，生成`layouts[1000]`。
2. 用户点击“重新获取选择的文件”，`ReplaceInputSelection`把`_files`替换为空列表并启动新扫描。
3. 新扫描很快加入2000行。
4. 旧布局线程完成并把`layouts[1000]`投递到UI线程。
5. `ApplyLayouts`按`_files.Count=2000`循环，访问`layouts[1000]`，抛`IndexOutOfRangeException`。
6. 该异常发生在Dispatcher回调中，若Quicker没有全局异常处理，可能直接终止进程。

即使新列表更短，也会出现“旧布局套到新行”或`FinalizeLayouts`读`_files[i]`越界（被布局线程catch后放弃整批布局），表现为目标路径长时间不刷新。

建议：

- `ReplaceInputSelection`开始时递增`_recomputeGeneration`、`_scanGeneration`、`_hashGeneration`，并设置“新会话/新数据集”标识。
- 布局线程只接受不可变快照：`FileItem[] snapshot = _files.ToArray()`，所有下标访问基于快照，不再读静态`_files`。
- `ApplyLayouts`增加三重校验：会话一致、代际一致、`layouts.Length == snapshot.Length`；不满足直接丢弃。
- 在数据替换后，等待旧布局线程退出（有上限）或让旧线程的结果因代际不匹配自然作废。

#### D-02 执行线程跨会话与`_execStop`复活（P0）

证据：

- `ExecutionWorker`（`:5354-5372`）循环读取静态`_execQueue`、`_execCursor`和`_execStop`。
- `PostExecutionCompleted`（`:5711-5734`）在结束时把`_execStop`置为`false`。
- `ResetRuntimeState`（`:420-505`）在新窗口加载时也会把`_execStop`置为`false`。

风险场景：

1. 旧窗口执行大文件复制，用户关闭窗口，`_execStop=true`，线程在`CopyFileEx`中暂时无法退出。
2. 用户重新打开窗口，`ResetRuntimeState`把`_execStop=false`，并准备新的`_execQueue`。
3. 旧线程完成当前文件后回到循环，看到`_execStop=false`，继续从静态`_execQueue`领取任务。
4. 结果：旧线程可能执行新窗口的队列，或在旧行词典上写状态；如果新旧路径重合，可能重复重命名/复制。

建议：

- 执行开始时创建`ExecutionSession`对象，包含`Id`、`volatile bool Cancelled`、`List<...> Queue`、`int Cursor`、计数器；工作线程只捕获该对象，不再读静态字段。
- `Window_Closed`只取消当前会话，绝不重置旧会话的`Cancelled`；新窗口创建新对象。
- 所有执行回调先校验`session.Id == _activeSession.Id`，不一致直接丢弃。
- 删除`PostExecutionCompleted`中对`_execStop`的全局复位，改为只复位当前会话的局部标志。

#### D-03 哈希线程启动失败导致`_hashRunning`永久为true（P1）

证据：`EnsureHashWorker`在`:2179-2250`先设置`_hashRunning=true`，随后`Thread.Start()`。当前没有`try/catch`包裹`Start()`。

后果：若线程创建失败（资源耗尽、宿主限制），`_hashRunning`永远为true，后续`EnsureHashWorker`直接返回；界面显示“计算中”，但没有任何线程在算，执行前校验也可能使用缺失哈希。

建议：

```csharp
_hashRunning = true;
try
{
    thread.Start();
}
catch
{
    _hashRunning = false;
    _hashStatus = "哈希线程启动失败";
    throw;
}
```

同时在线程`finally`中只在“当前代际仍属于自己”时复位，避免旧线程复位新线程的标志。

#### D-04 扫描发布线程的无限等待（P1）

证据：`StartScanInternal`（`:1722-1890`）创建多个扫描工作线程，发布线程在`:1835-1889`循环等待`chunkReady`和`workersRemaining`。

风险：

- 任一`Thread.Start()`失败，对应工作线程没有机会递减`workersRemaining`，发布线程将每50ms空转，永不结束。
- 某个工作线程因未捕获异常（如`OutOfMemoryException`）退出，未把分块标记为就绪，发布线程同样永久等待。
- `_scanning`保持true，后续刷新/执行前检查可能被阻塞。

建议：

- 每个`Start()`用`try/catch`，失败时按“该工作线程负责的分块全部标记失败/完成”处理，并递减计数。
- 发布线程增加总超时（例如按文件数与IO类型估算上限），超时后发布已完成部分并结束扫描，状态栏提示“部分文件扫描超时”。
- 工作线程最外层`try/finally`确保递减计数并标记剩余分块。

#### D-05 执行线程启动失败导致永不完成（P1）

证据：`Execute_Click`在`:5320-5352`按并行度循环`new Thread(...).Start()`，事先把`_execWorkers`设为并行度，没有处理`Start()`异常。

后果：只要一个线程启动失败，`_execWorkers`永远不会减到0，`PostExecutionCompleted`不执行；`_executing`保持true，按钮不可用，用户点击关闭会进入“等待执行完成”的取消循环。

建议：

- 逐个启动，启动成功才递增`_execWorkers`；失败则回退为更少线程或同步执行剩余任务。
- 全部启动失败时立即复位`_executing=false`，弹出错误，不进入执行态。
- 为执行增加“无进展超时”监控，超时后提示用户并可强制取消。

#### D-06 `Window_Closed`清理不完整（P1）

证据：`Window_Closed`（`:6049-6164`）停止了主要定时器和线程，但遗留：

| 遗留项 | 影响 |
|---|---|
| `_layoutWorkerCount` | 重开后实时差异更新可能被旧计数永久延迟 |
| `_execQueue` | 持有文件行与路径字典，旧会话执行线程仍可能读取 |
| `_execDirs` | 每次执行累积的目录集合 |
| `_data` | 可能持有`files`/`origPaths`/`targetPaths`整批输出 |
| `_winContext` | 持有Quicker上下文对象 |
| `_lastCaret` | 持有`TextPointer`，可能间接保留FlowDocument |
| `_templateHashCheckKey` | 仅字符串，影响小 |
| `_scanning`/`_previewDirty` | 重开后状态继承 |
| `_presetPopup` | 未显式`IsOpen=false` |

建议：把清理拆成幂等的`ShutdownSession()`：

1. 停止所有定时器并置空。
2. 取消并等待线程（短超时），清除线程引用。
3. 关闭Popup，清空`ItemsSource`，解除事件。
4. 释放COM/Process/Dialog。
5. 清空大集合与静态引用。
6. 最后置空`_window`、`_config`、`_data`、`_winContext`。
7. 整个方法用`try/finally`，每步单独`try/catch`，保证后续步骤继续。

#### D-07 哈希缓存“旧代际晚写”和“重新获取后不失效”（P1）

证据：

- `HashWorker`（`:2313-2352`）在计算完成后先写`_hashCache`，之后才检查`_hashStop`和代际。
- `EnsureHashWorker`（`:2179-2250`）遍历全部`_files`并查缓存。
- `ReplaceInputSelection`（`:3734-3797`）替换文件列表，但没有清空`_hashCache`。
- `ApplySelectionDiff`删除文件（`:3844-3956`）也没有移除对应缓存项。

后果：

1. 用户在哈希过程中修改算法/重新获取/执行重命名，旧线程仍把旧算法或旧文件内容的哈希写入缓存，可能覆盖新线程刚写入的正确值。
2. 用户重新获取同一路径的文件，但文件内容已在外部改变，缓存仍返回旧哈希，最终文件名中的校验码错误。
3. 删除的文件缓存永久留在字典中，长会话持续增长。

建议：

- 缓存键改为`路径|长度|最后写入时间Ticks|算法`。
- 写入前校验`generation == _hashGeneration && session == _activeSession`，不匹配直接丢弃。
- `ReplaceInputSelection`、差异删除、执行重命名后，按路径清理或整体失效缓存。
- 设置容量上限（如10万项）和简单LRU/分段清理。

#### D-08 哈希读取与执行改名的共享冲突（P1）

证据：`ComputeHashHex`（`RenamerCore.cs:1396-1411`）以`FileShare.ReadWrite`打开文件，不包含`FileShare.Delete`；执行阶段可能对同一文件做移动/重命名。

后果：

- 哈希线程仍持有读句柄时，`File.Move`/`File.Delete`可能因共享冲突失败，执行进入重试；网络/云端文件重试成本更高。
- 文件在哈希过程中被外部修改时，得到的是“变化中的内容”的哈希，且没有大小/修改时间前后校验。

建议：

- 哈希读取使用`FileShare.ReadWrite | FileShare.Delete`，允许并发改名/删除；读取后比较前后`Length`和`LastWriteTimeUtc`，不一致则重算或标记失败。
- 执行开始前确保哈希任务已停止或完成；若必须并行，捕获共享冲突并按“稍后重试”处理。

#### A-01 统一会话与生命周期（P0，架构根因）

当前项目用多个独立代际号（`_scanGeneration`、`_hashGeneration`、`_recomputeGeneration`）和多个独立停止标志（`_hashStop`、`_execStop`、`_selectionReaderStop`）拼装生命周期。每个异步路径都要“记得”检查对应标志，漏一处就产生跨会话写入。

建议引入单一的`WindowSession`：

```csharp
private sealed class WindowSession
{
    public readonly int Id;
    public readonly Dispatcher Dispatcher;
    public volatile bool Closed;
    public volatile bool CancelRequested;
    public List<Dictionary<string, object>> Files;
    public List<Dictionary<string, object>> Rows;
    public Dictionary<string, string> Config;
    public Dictionary<string, string> HashCache;
    public readonly object Sync = new object();
}
```

所有线程、定时器、Dispatcher回调、COM回调都捕获`WindowSession`，入口统一执行：

```csharp
private static bool IsCurrent(WindowSession session)
{
    return session != null && !session.Closed && ReferenceEquals(session, _session);
}
```

这样即使某个路径忘记检查具体代际，也不至于写入新窗口。

#### A-03 不可变数据快照（P0）

布局线程当前直接读`_files`和行词典，这是所有数据竞争的根源。建议：

- UI线程维护`_files`和`_rows`，后台只接收`FileItem[] snapshot`。
- `FileItem`中的可变字段（目标路径、动作、状态、哈希）不在后台直接写；后台返回`LayoutResult[]`，由UI线程按索引应用。
- 任何可能改变`_files`数量的操作（重新获取、差异增删、扫描批次）都创建新快照，并让旧布局结果因“快照版本不匹配”作废。

`ApplyLayouts`至少增加：

```csharp
if (!IsCurrent(session) || generation != _recomputeGeneration)
    return;
int n = Math.Min(_files.Count, layouts.Length);
if (layouts.Length != expectedCount)
    return; // 数据集已变化，丢弃旧结果
```

#### P-01 全局并发预算（P1，性能根因）

当前并行入口：

| 入口 | 最大并发 |
|---|---|
| 扫描工作线程 | 4~12 |
| 哈希线程 | 1 |
| 布局`RunIndexedParallel` | 最多8 |
| 布局内目标比较 | 最多8，且每个比较可进入BLAKE3`Parallel.For`（最多8） |
| 执行工作线程 | 1~8，每个可做执行后校验哈希 |
| BLAKE3内部分块 | 按CPU档位最多8 |

理论上可同时出现数十个CPU/IO线程。建议：

- 设立全局`SemaphoreSlim`/自定义令牌桶，按CPU核数分配“重计算令牌”；BLAKE3内部分块只在拿到令牌时并行，否则串行。
- 用`[ThreadStatic] bool _insideParallelWorker`标记：已经处于布局/执行工作项时，内层哈希不再`Parallel.For`。
- 执行校验与后台哈希共享同一预算，避免“执行8路+校验8路+哈希1路”同时跑。
- 网络路径按主机限流，避免12个线程同时打同一NAS。

#### P-02 UI线程同步布局/比较（P1）

`RecomputeAll(true)`用于执行前、预设加载等场景，会同步等待布局；当行数超过阈值或目标冲突需要比较内容时，`FinalizeLayouts`可能在UI线程调用`TryCompareFileContent`→`ComputeHashHex`。文件大或网络慢时，界面完全冻结，用户无法取消。

建议：

- UI线程只发起异步布局，显示“正在计算目标”状态和取消按钮。
- 执行前如果必须等待布局，使用`await`/Dispatcher帧回调分片等待，不阻塞消息泵。
- 内容比较和哈希永远不在UI线程执行。

#### P-03 BLAKE3分块屏障（P2）

`ComputeBlake3Hex`按读缓冲（最大1MB）处理完整分块，每处理一个缓冲调用一次`Parallel.For`。1GB文件约1024次并行调度与屏障。虽然每次分块数1024、计算量足够摊薄开销，但大文件仍可优化：

- 将读缓冲提高到4~8MB（对应`_blake3CvBatch` 256KB~512KB/线程），减少屏障次数。
- 或累积多个读缓冲后一次性并行分块，再顺序合并CV。
- 优化前后必须用官方向量和大文件边界向量回归，确保哈希不变。

#### P-04 实时选择的COM开销（P2）

`GetExplorerSelectedPaths`每轮都`Activator.CreateInstance`创建`Shell.Application`，枚举所有资源管理器窗口，读取`Document`/`SelectedItems`，再释放部分对象。350ms一轮时，CPU和GC开销明显，且未释放的RCW会累积。

建议：

- 优先使用WinEvent回调提供的`hwnd`，只查询该窗口，不枚举全部窗口。
- 在STA读取线程内缓存`Shell.Application`实例（线程亲和），窗口关闭时释放。
- 增加“选择未变化”快速判定，避免重复构建列表。

## 6. 建议整改设计

### 6.1 会话与数据流

```text
UI线程
  ├─ 创建 WindowSession（Id、Config、Files快照、Rows、Cancellation）
  ├─ 用户操作 → 更新会话数据 → 生成新快照版本
  └─ 接收后台结果 → IsCurrent(session) && version匹配 → 应用到UI

后台线程
  ├─ 只读快照
  ├─ 只写自己的结果数组/局部对象
  └─ Dispatcher回调携带 session + version
```

关键原则：

1. 后台线程不直接读写`_files`、`_rows`、`_config`、`_hashCache`。
2. 所有回调先校验会话，再校验版本，最后才碰UI。
3. 清理只针对当前会话；旧会话对象由最后一个引用释放。

### 6.2 执行会话

```csharp
private sealed class ExecutionSession
{
    public int Id;
    public volatile bool Cancelled;
    public List<Dictionary<string, object>> Queue;
    public int Cursor;
    public int Workers;
    public int Done;
    public int Errors;
    public long Bytes;
}
```

工作线程循环条件改为`!session.Cancelled`，不再读静态`_execStop`；完成回调校验`session == _execSession`。

### 6.3 布局快照与结果应用

```csharp
FileItem[] snapshot = _files.ToArray();
int version = ++_dataVersion;

ThreadPool.QueueUserWorkItem(delegate
{
    LayoutResult[] results = Compute(snapshot);
    Post(dispatcher, delegate
    {
        if (!IsCurrent(session) || version != _dataVersion)
            return;
        ApplyLayouts(snapshot, results);
    });
});
```

`ApplyLayouts`不再读静态`_files.Count`，而是按`snapshot.Length`和`results.Length`一致性处理。

### 6.4 COM释放模板

```csharp
object document = null;
object selected = null;
ArrayList items = null;
try
{
    document = InvokeCom(window, "Document", false);
    selected = InvokeCom(document, "SelectedItems", false);
    items = GetComItems(selected);
    // 使用 items
}
finally
{
    ReleaseComItems(items);
    ReleaseComObject(ref selected);
    ReleaseComObject(ref document);
}
```

注意：只释放本方法明确获取并登记的RCW；不要释放调用方传入的对象。

### 6.5 关闭流程

```text
Window_Closing
  ├─ 执行中：请求取消，等待当前文件完成，可配置超时
  └─ 非执行中：允许关闭

Window_Closed
  ├─ ShutdownSession()
  │   ├─ 停止定时器
  │   ├─ 取消/等待线程（短超时）
  │   ├─ 关闭Popup/对话框
  │   ├─ 释放COM/Process
  │   ├─ 清空集合与静态引用
  │   └─ 最后置空窗口上下文
  └─ try/finally 保证每一步独立执行
```

## 8. 各团队结论

### 8.1 架构组

**有条件通过。** 原分析对风险的定位准确，但根因不是单个方法遗漏，而是“静态单例状态+多套代际号+可变共享集合”的组合。若不引入统一会话和不可变快照，后续每加一个异步功能都会重复出现同类问题。P0-1、P0-2、P0-3必须同时完成，不能只修表面计数。

### 8.2 开发组

**有条件通过。** 已确认的具体缺陷包括：`ReplaceInputSelection`越界路径、执行线程跨会话、线程启动失败卡死、哈希缓存旧写覆盖、COM释放不完整。建议按P0顺序修复，每项配套失败注入测试；不要在未加会话校验的情况下继续扩展执行/实时获取功能。

### 8.3 性能组

**有条件通过。** BLAKE3本身的优化方向正确，单文件哈希不再是主要瓶颈；当前更大的性能风险来自嵌套并行、UI线程同步布局、实时选择COM轮询和哈希缓存全量扫描。建议先做全局并发预算和UI线程解阻，再做BLAKE3缓冲调优，避免“局部优化、整体更慢”。

### 8.4 测试与运维视角

**验收待Windows实机。** 静态审查无法证明COM引用计数、WinEvent投递和Quicker宿主异常策略。交付前必须完成第7.2节场景，尤其是“执行中关闭再打开”和“布局中重新获取”两个高风险路径。
